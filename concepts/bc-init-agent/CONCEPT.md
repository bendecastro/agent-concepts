# Concept: bc-init-agent

User-invoked adaptive initializer. Code, ops and hybrid scaffold the visible layout (work items in `work/`, decisions and research in `docs/`, root `glossary.md`, agent mechanics in `.bc-agent/`); learning and knowledge keep the `.bc-agent/` vault. Hybrid adds the paths the hosted `teach` adapter maps. The visible layout has deterministic tests but has not yet been pressure-tested with a consuming agent.

## Design decisions

- **Visible layout for code, ops and hybrid (2026-11-12).** Provenance: the "Resolved decisions" of [the visible-layout plan](../../docs/plans/implemented/bc-init-agent-visible-layout.md), agreed with the owner; this is its work package W1. Knowledge is visible and `.bc-agent/` holds agent mechanics only (`AGENTS.md`, `map.md`, `log.md`, `conventions/`, `references/`, `templates/`). Work items move through `work/1-planned/`, `2-active/`, `3-done/<year>-<month>/`, `4-dropped/`; the folder is the status, so the work-item template has `Why:`, `Done when:`, optional `Issue:`, `## Steps`, `## Outcome` and no `Status:`. Ideas are lines in `work/0-ideas.md`; a plan is a work item, so no plan template or plans folder is generated. Decisions and research live in `docs/decisions/` and `docs/research/`; empty folders carry `.gitkeep`, and the four `work/` stage folders keep theirs permanently so every stage stays in git when empty. `docs/PRD.md`, `ARCHITECTURE.md`, `.agents/skills/` and `.agents/agents/` are named in the table and created on first need, not as placeholders. `tasks/`, `project/`, `decisions/`, `research/`, `scratch/`, `out-of-scope/`, `index.md`, `home.md`, Obsidian settings and `conventions/planning-workflow.md` are no longer generated for these archetypes.
- **Generated work index and stages (owner decision 2026-11-16).** Visible layouts get `.bc-agent/scripts/work_index.py` (Python stdlib, ported from project A's `work-index.mjs` script), a `work/README.md` with the generated block's markers, a `Stages:` line (default `now, next, later, unscheduled`) and an "every open item has a `Stage:` line" rule in the generated Work items section, the index run in the Begin/Finish-a-step/Finish-or-drop rows, and `Stage:` directly under `Done when:` in the template. Refresh only the script with `cp "$AGENT_CONCEPTS/concepts/bc-init-agent/body/work_index.py" .bc-agent/scripts/`; `--force` also refreshes it, along with every other `.bc-agent/` file. The canonical copy is `body/work_index.py`, which `bc-work-sync` relies on. The generated text now says "status folders" for `1-planned/`…`4-dropped/`, since "stage" names the `Stage:` value. A fresh `work/README.md` contains the generated empty index and passes `--check`. Edges: `bc-wiki-maintain`'s agent-mechanics check allows `scripts/` (updated in the same change, its tests failed without it); `bc-plan-to-pipeline`, `bc-drain-issues`, `triage` and `improve-codebase-architecture` create or move items through the generated template and work-item rules (each SKILL says so), so they pick up the `Stage:` line and the index run from the project; `handoff`, `diagnosing-bugs`, `domain-modeling`, `prototype` and `teach` only resolve paths and are unaffected. Those skills still say "stage folders" for the status folders; not renamed here. Upgrade: [MIGRATIONS.md](MIGRATIONS.md#work-index).
- **Blocked-by ordering (owner decision 2026-11-22).** The work-item template has `Blocked by:` under `Stage:` (full item names or `nothing`), and the generated Work items section adds four rules: every open item has a `Blocked by:` line; a building block gets its own item; look for overlap in open items and the ideas file before creating one; one item, one deliverable. `work_index.py` rejects a missing line, unknown or dropped blockers, self-blocks and cycles, and orders the table topologically (active, then ready, then most open items transitively unblocked, then the `Stages:` order, then name) with `#`, `Waits on` and `Unblocks` columns; a blocker in `3-done/` is satisfied. Provenance: the owner's adoption of this rule set in one of their projects (project B), whose script and tests were ported here with the generic default stages kept. Edges: `bc-plan-to-pipeline`, `bc-drain-issues`, `triage` and `improve-codebase-architecture` write items from the project's template under its work-item rules, so they pick up the line from the project (as with `Stage:`); `bc-work-sync` runs the script and now reports missing and invalid `Blocked by:` lines (updated in the same change); `bc-wiki-maintain` only allows the `scripts/` folder and is unaffected. Upgrade: [MIGRATIONS.md](MIGRATIONS.md#blocked-by). Since 2026-11-23 the script accepts an open item without a `Stage:` line and sorts it after every stage (an unknown stage is still an error); the generated rule still asks for the line. Why: several projects keep stage-less items, and their local copies already accepted them, so the canonical copy blocked the owner-order rollout.
- **Owner order (owner decision 2026-11-22).** An optional `work/order.md` holds the owner's ranking of open items as a numbered list (`1. 012-search-ranking`; other lines ignored). `work_index.py` ranks active items first, then the planned items an active item is transitively blocked by (spec amendment 2026-11-22, so blockers of active work are not pushed behind a ranked unrelated item), then puts listed items in list order, ahead of unlisted ones and ahead of the ready/unblocked/stage tiebreaks; blockers still win; an unlisted blocker does not inherit its listed item’s rank. Dashboard-written orders list every open item, so this affects only hand-written partial lists. The order applies when every item says `Blocked by: nothing`. Names in `3-done/` or `4-dropped/` (and their month folders) are skipped unless an open item has the name; order-line digits are ASCII only; an unknown or repeated name is an error. The three tiers (active, blockers of active, other planned) apply with or without the file (spec amendment, round 3); without it there is only no owner rank. `Blocked by:` stays required on every open item even when `order.md` exists. The format and key are a spec shared with the owner's dashboard, which reads and writes the same file (unknown/repeated names are warnings there). The generated Work items section gains one rule naming the file. Edges: `bc-work-sync` runs the script, so its `--check` now also reports bad `order.md` names (its SKILL says so, updated in the same change); other writers of items are unaffected. Upgrade: [MIGRATIONS.md](MIGRATIONS.md#owner-order). Since 2026-11-23 (owner request) `--check` also fails while `order.md` leaves out an open item or lists an item above one it waits on, naming where an unlisted item goes (directly above the first listed item that waits on it, else the bottom), and the generated Work items section adds "Never reorder `work/order.md`; place what you add" (check with the owner before a `Blocked by:` line that inverts the order). The table is still built from a partial or inverted file; only `--check` refuses it. Why: the dashboard writes every open item and refuses a blocker below its dependant, so these faults come only from agents, and an agent that added an item and a blocker without listing it sent three of the owner's ranked items to the bottom. `bc-work-sync`'s SKILL names the new faults (same change).
- **Staged validation, one gate command, CI on it (owner decisions 2026-11-19).** Visible layouts get a `conventions/validation.md` with three stages, one owner each: While working (worker, job or reviewer: typecheck, lint, affected unit tests; no browser/e2e tests, no full gate; 60 s budget), Full gate (the integrating session: `<offload-wrapper> --budget 300 -- scripts/gate` in the background with a wake, once per integrated tree, tree SHA and result recorded for reviewers to reuse, one per host, rerun only failing tests for a flake, two over-budget runs in a row open a work item before more features; every browser/e2e test runs here) and Release. `./scripts/gate` runs its steps directly, with no `<offload-wrapper>` inside, so the generated `.github/workflows/gate.yml` runs it unchanged on a clean checkout; the root `AGENTS.md` says to check the latest trunk CI run before landing, red blocks. The stub gate exits non-zero until filled: a vacuous green gate would report success for checks nobody wrote, which is how a trunk stays red or unmeasured unnoticed. Provenance: project A's `validation.md` (stages and full-gate rules) and the agent-time-sinks council memo (2026-11-19: an empty TODO validation page was filled with "full gate before every commit", packets pasted it into workers, and CI was red 30/30 unnoticed). `VALIDATION` for learning and knowledge is unchanged.
- **Ops keeps its operational knowledge.** `docs/components/` with the `component` and `finding` templates; findings go to `docs/research/`, plans are work items.
- **Open questions are work, not a folder (owner decision 2026-11-12).** Ops and hybrid no longer generate `docs/open-questions/` or an open-question template. The generated `.bc-agent/AGENTS.md` of every visible-layout archetype says, with the work-item rules: a question that blocks a piece of work is a step in that work item; a standalone question someone must investigate is a planned work item whose answer lands in `docs/research/`; one not worth an item yet is a line in `work/0-ideas.md`. Why: `work/` stays the single place that shows what is pending.
- **Hybrid = ops layout plus exactly the teach adapter's mapped paths** under `.bc-agent/` (`learning/`, `sources/`, `concepts/` with `entities/` and `syntheses/`, `questions/`, `sessions/`, `references/teach-skill.md`, `references/teach-resources.md`, `templates/learning-session.md`, `index.md` as the teach catalog). Why: `teach` pins those paths, and changing them belongs to the teach redesign.
- **Hybrid has one glossary (owner decision 2026-11-12).** The hybrid adapter maps `teach`'s Glossary to the project's root `glossary.md` (`../glossary.md` from `<teach-root>`), shared with the project: `teach` adds and refines the terms the learner needs in the file's one-line format and does not remove or redefine project terms without asking; `domain-modeling` and planning skills keep using the same file. Hybrid no longer generates `.bc-agent/project/overview.md`, and `.bc-agent/project` counts as earlier layout for hybrid as for code and ops. `is_valid_teach_adapter` accepts exactly two maps, the vault map and the hybrid map, which differ only in the Glossary row; the learning archetype keeps the vault map. Provenance: resolved decisions of [the visible-layout plan](../../docs/plans/implemented/bc-init-agent-visible-layout.md).
- **Learning and knowledge keep the vault, byte-identical to before.** Why: `teach` reads exact vault paths and its tests pin them. `tests/test_visible_layout.py` compares their output with the scaffold at `e27f2e6`.
- **Existing projects are not migrated by the scaffold, and are refused by default.** On a project with earlier-layout paths under `.bc-agent/`, a visible-layout run writes nothing, names the paths and exits non-zero; `--allow-earlier-layout` creates the missing files beside the old ones instead. Why: two sets of homes for the same knowledge would both look current, and plan Q22 moves a project deliberately in one pass. See [MIGRATIONS.md](MIGRATIONS.md#visible-layout).
- **Migration is a separate, dry-run-first mode that does only the mechanical part (W4, 2026-11-12).** `--migrate` prints the plan; `--migrate --apply` moves whole files with `git mv`, creates the missing layout files, replaces `.bc-agent/AGENTS.md`, deletes only placeholders and unmodified generated files, rewrites relative Markdown links, stages and does not commit. Everything needing a reading of content (task lists, plans, overviews, findings, open questions, catalogs, unrecognised files) is printed with the owner's rule and left untouched; the skill body tells the agent how to apply each rule. Why: a move is safe to automate, but deciding which tasks are still open or what an overview's terms are is not, and inventing work-item fields for finished tasks would be fiction. Owner decisions (2026-11-12): only open work becomes items, finished lists stay as one dated research record; `docs/adr/` moves to `docs/decisions/`; issue drafts live inside their parent item; a project without a vault gets a fresh scaffold. A wikilink naming a moved file becomes a relative Markdown link (owner decision 32): the Obsidian settings are retired and plain links resolve in any viewer. A bare name matching several files is left and reported rather than guessed, and wikilinks to files that stay are untouched, since the change is about not breaking links, not converting a vault. Provenance: the plan's owner decisions 27–30 and 32 and a trial on clones of one code and one ops project.
- **`--force` stays inside `.bc-agent/`.** Root `glossary.md`, `work/` and `docs/` hold the project's own content and are never overwritten; root `AGENTS.md` needs `--force-root`.
- **Project agents live in `.agents/agents/` (owner decision 2026-11-12).** The `project-agents` row, previously undecided (`—`, "ask the owner"), names `.agents/agents/`, created on first need, one `local-<name>.md` file per agent beside `.agents/skills/`. Why: one `.agents/` folder for both kinds of project extension, with the same `local-` prefix that separates project entries from shared ones.
- **Generated text redirects skill defaults to the table.** `.bc-agent/AGENTS.md` tells agents to use the table's path when a shared skill names its own default (for example `docs/adr/`), and root `AGENTS.md` keeps `codebase-docs` off the table's record paths. Why: shared skills are written for several layouts, and until the consumer skills read the table (W3) this rule is the only redirect.

- **W3 review fixes (2026-11-12).** A large work item's folder holds `plan.md` (its `## Steps` are the slices) and `requirements.md`, plus any evidence; no separate slice files, because the steps already are the slice map (decision 10 refined in review, pending the owner's confirmation; recorded in the plan). The visible runway page keeps the default `docs/research` and `docs work` in its snippet and tells the agent to substitute the table's research and work paths when the project changed them. The map upgrade note fires only for an inline-code bullet whose target is an existing file inside `.bc-agent/`, so a bullet naming a project file created on first need (for example `docs/PRD.md`) is not flagged. Standalone teach state is matched by exact directory-entry name, so a hybrid project's shared root `glossary.md` is not mistaken for `GLOSSARY.md` on a case-insensitive filesystem. Provenance: the W2/W3 review of [the visible-layout plan](../../docs/plans/implemented/bc-init-agent-visible-layout.md).

- **Validation page names the test levels (2026-11-17).** Visible-layout `conventions/validation.md` lists tdd's three test levels with `Level 3: off` and the `.hypothesis/`-style cache rule (gitignored, Syncthing-ignored machine-local state). Only visible archetypes get it: learning/knowledge vaults keep the base template byte-identical. No migration: existing projects gain the entry when their first property test lands. Covered by `test_validation_page_names_three_test_levels_with_level_3_off`. Later the same day the Level 3 entry became a bare `Level 3: off` followed by commented examples of the owner-only `Level 3: on` and `Level 3 declined` lines, copied from tdd's `formal.md` (covered by `test_validation_page_level_3_is_off_with_owner_only_on_and_declined_formats`).

- **The scaffolded gate names no machine tool (2026-11-19).** `validation.md` tells agents to start the scaffolded gate script through the machine's offload wrapper if its agent instructions name one, with a measured, non-enforced 300 s budget; its header mentions the wrapper but not the budget. scaffold.py has no machine-config seam (only the vault path and archetype), and adding one would be speculative. Why: scaffolded projects and this repository are public; a stranger's machine may have no wrapper.

- **Design README (2026-11-21).** Code, ops and hybrid scaffolds write `docs/design/README.md` (current truth vs the project's decision log, where a rule lives, the before-adding-a-control step, empty Pages and Checks lists; no fixed page list) and a prose line in `.bc-agent/map.md` routing design, UI and CLI wording work to it. Why these kinds: they ship or operate something people use (GUI, TUI, CLI, or operated tools); learning and knowledge vaults have no product surface, and their output stays byte-identical to the base. The map line is prose, not a bullet, because map bullets must be in-vault links. Existing projects get the README on their next run (never overwritten); an existing map that lacks the line produces an upgrade note. No new "Where things go" role: the owner decided day one creates only the README and the map line. The method is `ui-design`'s `design-framework.md`. Covered by `tests/test_design_readme.py`.

## Interface: the "Where things go" table

Later work packages and other skills read project paths through this contract, not by assuming them.

- **Location and heading.** `.bc-agent/AGENTS.md`, section `## Where things go`.
- **Columns.** A Markdown table with header `| Role | Path | Notes |`. Path is a backticked path relative to the project root, or `—` when the role has no decided path. Notes say, among other things, "created on first need" for a path that may not exist yet.
- **Role keys** (`LAYOUT_ROLES` in [`body/scaffold.py`](body/scaffold.py)): `work-planned`, `work-active`, `work-done`, `work-dropped`, `ideas`, `decisions`, `research`, `glossary`, `requirements`, `architecture`, `project-skills`, `project-agents`. Ops and hybrid add `components`; hybrid adds `teach-workspace`. Optional, never generated (`OPTIONAL_LAYOUT_ROLES`): `agent-extras`, whose Path cell lists comma-separated `.bc-agent/` entries a tool reads by path (for example `` `.bc-agent/autoresearch/` ``); `bc-wiki-maintain`'s lint reports every other entry under `.bc-agent/` that is not agent mechanics. The shared parser returns only the first backticked path of that cell, so a reader of the full list reads the raw cell.
- **Parser.** `parse_where_things_go(text)` in `body/scaffold.py` returns `{role: path}`. A backticked path is unwrapped; a plain path is returned stripped; only `—`, `-` or an empty cell maps to `""` (undecided). The heading must be a whole line (trailing spaces and CRLF tolerated; `### Where things go` does not count). It raises `ValueError` when the heading is missing, when the section has no table rows, or when a role appears twice. `where_things_go_table(archetype)` writes the table from `layout_rows(archetype)`.

## Interface: migrate mode

`scaffold.py --root <repo> --slug <slug> --archetype code|ops|hybrid --migrate [--apply]`. Exit 1 with nothing written on a refusal (not a git repository root, uncommitted changes listed, no `.bc-agent/`, table already present, learning or knowledge archetype, missing `--archetype`, a destination already present as a different file). Output, in order: `Repo:`, `Branch:`, `Archetype:`, then the sections `MOVE` (`old -> new`), `CREATE`, `REPLACE`, `DELETE`, `KEPT (review by hand)`, `NEEDS JUDGMENT` (`path — N lines|N files — rule`), `LINKS`, `OTHER REFERENCES`, each item indented two spaces and `(none)` when empty; then `Totals:` and the apply command. `--apply` adds an `Applied:` line and ends with the reminder to work through the judgment list and commit. Details: [MIGRATIONS.md](MIGRATIONS.md#migrate-mode).

## Open items

- **Merge is held.** The deploy symlinks point into `body/`, so merging this concept to the main checkout makes it live immediately. The merge waits until the consumer skills (W3) read the "Where things go" table.
- **Pressure test.** The skill's visible-layout process steps (PRD question, location suggestion, sync-folder warning, earlier-layout refusal) have not been run against a consuming agent; [tests/scenario.md](tests/scenario.md) checks 8a–8d are the packet.

- **Recon before grilling, then scaffold.** The skill now treats initialization as adaptive onboarding rather than blind file generation: inspect git/GitHub state, project shape, docs, build/deploy markers, and risk signals first; summarize what was found; then grill only the missing decisions. Empty folders get project-intent questions, active projects get integration questions, operational/system folders get component/evidence questions, learning folders get `teach`/learning-plan questions, knowledge folders get raw/source/entity/concept questions, and old/messy projects get reconciliation/migration questions before anything is written.
- **Wiki archetypes from real user patterns.** The scaffold recognizes `code` (project execution: work items, decision records, research including architecture reviews, references), `ops` (system operations: code plus components; open questions are work items), `learning` (teach-backed study vaults), `knowledge` (immutable raw sources → compiled source/entity/concept/synthesis wiki), and `hybrid` when a repo needs more than one durable mode.
- **Modes keep init from becoming magical.** The skill distinguishes recon-only, plan-init, apply-scaffold, and migration-assist modes. The deterministic scaffold remains additive; moving or copying existing docs into the workspace is a separate, explicitly approved migration step.
- **Deterministic scaffolding via a script.** File-tree generation from a fixed template is exactly the kind of thing an LLM does unreliably, so `body/scaffold.py` writes the base tree with `__SLUG__`/`__DATE__` substitution and optional archetype seed files via `--archetype code|ops|learning|knowledge|hybrid`. The skill body handles what needs judgment: environment recon, archetype selection, targeted grilling, plan proposal, the clobber guard's follow-up, conservative seed edits, the publish.yaml offer, and the commit. (AGENTS.md "scripts for anything an LLM does unreliably".)
- **Architecture runway nudges by a computed Git-history signal, not calendar time.** Code, ops and hybrid include `conventions/architecture-runway.md`, which counts commits touching the durable project surfaces since the last commit naming an architecture review and asks agents to nudge for `/improve-codebase-architecture` when that count reaches its threshold or structural friction appears. This remains advisory and only applies when the skill is present in the repo-local skill map.
- **Additive idempotency (never destructive).** The script creates only the files that are missing and leaves every existing file untouched; re-running changes nothing, and it **never deletes** (only `mkdir` + `write_text`, gated on non-existence). This makes it safe to re-run and safe to plug into an existing project — an existing root `AGENTS.md` or any pre-existing vault page is preserved verbatim (the existing root `AGENTS.md` is flagged for a manual pointer-merge). Overwriting is opt-in only: `--force` for files under `.bc-agent/`, `--force-root` for the root `AGENTS.md`; `--dry-run` previews. When an existing instruction file needs a pointer to a newly added scaffold file, the script prints upgrade notes for the running agent to merge by hand instead of overwriting. Chosen over the original "refuse if the vault exists" guard because that blocked the realistic case (dropping the workspace into a repo that already has some of these files).
- **publish.yaml: offer-then-confirm (user's choice).** The skill drafts a repo-specific allow rule following the existing publish-policy schema and offers to append it to `~/.config/agent-concepts/publish.yaml` after the user confirms; it never pushes that change (self-amendment immunity). This closes the loop with `bc-drain-issues`, whose preflight needs the repo authorized for AFK push and claim-branch coordination.
- **Map links participate in maintenance (2026-08-31).** The generated `map.md` uses real relative Markdown links for every target inside the vault, so `bc-wiki-maintain`'s existing `links()` parser and resolver can validate and count those graph edges. Future map entries follow the same in-vault-only rule; external source-tree references remain inline code because they cannot enter this vault's graph and would otherwise create broken-link findings. Existing maps remain untouched by the additive scaffold and receive an upgrade note instead.
- **One-time map migration stays outside the injected body.** The existing-vault procedure lives in [`MIGRATIONS.md`](MIGRATIONS.md), where a future maintainer can find it without loading a one-time operation into every initialized agent session.
- **Planning intent trigger.** The root/vault instructions now tell agents to ask whether to enter `/bc-plan-to-pipeline` when the human sounds like they are planning codebase work, and to offer `/improve-codebase-architecture` first for architecture runway. Concrete edit/fix requests still proceed normally.
- **Research vs actual PRDs (learning/knowledge vault).** The generated workflow distinguishes exploratory research/evidence (`research/`) from plans/PRDs that were actually drafted or published (`project/` / parent issues), so architecture reports and investigations do not get mislabeled as PRDs.
- **qmd registration by default at close-out, opt-out (replaced the short-lived `--qmd` scaffold flag, 2026-07-13).** The scaffold itself is qmd-free — no flag, no generated `references/qmd.md`, nothing per-repo (project-local `.qmd/` indexes shadow the global registry and can't be committed; see `concepts/qmd/`). Instead the skill's close-out appends the new vault to the synced global canon (`<owner-scripts>/config/qmd-collections.yml`) and runs `<qmd-setup-script>`, asking only whether the user wants the vault excluded. Default-on because the realistic failure is a vault silently never joining the index. **Visible layout (owner decision 2026-11-12):** step 9 applies to code, ops and hybrid too, as two collections printed by `bc-wiki-maintain`'s `wiki_lint.py --qmd-entry <slug>` from the project's table: `<slug>` rooted at `.bc-agent/` and `<slug>-project` rooted at the repository with a pattern covering only the searchable roles' paths. Two because qmd skips hidden path parts, so a repository-rooted collection cannot index `.bc-agent/`; the bare slug stays on `.bc-agent/` so an already-registered project keeps its entry and adds one. The generator lives in the lint, so the entry and the registration check have one implementation; a test pins the skill's sample to its output. An opt-out is a line containing "excluded from the global qmd index" in `.bc-agent/AGENTS.md`.
- **No promotion timer for the visible layout (owner decision 2026-11-12).** Step 10 is skipped for code, ops and hybrid: promotion existed to move log entries into vault pages, and in the visible layout agents write decisions and research straight to the role folders while `log.md` is a plain journal. The lint still applies. The hybrid teach adapter says `bc-wiki-maintain` does not promote log entries in that layout.
- **Wiki-maintain timer: offer-then-confirm (2026-08-29).** Close-out
  offers to copy the `bc-wiki-maintain` runner templates to
  slug-suffixed user units so promotion can run overnight from day one.
  Confirmed by the user as offer-then-install, not mention-only and not
  default-on. The scaffold stays timer-free. qmd refresh is not this
  timer. Provenance: `concepts/bc-wiki-maintain/body/runner/`.
- **TODO stubs, not invented facts.** `validation.md`, `file-layout.md`, `references/*`, and the glossary ship as explicit TODO stubs for the project's agents to fill — preserving epistemic honesty rather than fabricating project facts.
- **Teach integration is an explicit adapter, not a second tutor.** Learning and hybrid overlays
  emit `.bc-agent/references/teach-skill.md` with the approved mission/review/records/knowledge/
  glossary/session mapping (hybrid's glossary row names the shared root `glossary.md`). The initializer owns host schema/orientation; teach owns pedagogy,
  evidence, and SRS state. Hybrid learning/knowledge overlays keep raw and compiled material in
  the mapped `sources/` and `concepts/` homes (entity/synthesis subtrees live below `concepts/`)
  rather than generating parallel `raw/` or `wiki/` trees. Existing standalone teach files remain
  in place, and any competing homes are reported for a user decision rather than migrated. A host
  choice alone never migrates state; teach's separate explicit migration operation is destructive,
  warns that originals will be deleted, verifies every destination first, and preserves originals
  when verification fails.
