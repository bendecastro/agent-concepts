# Concept: bc-init-agent

User-invoked adaptive initializer. Code, ops and hybrid scaffold the visible layout (work items in `work/`, decisions and research in `docs/`, root `glossary.md`, agent mechanics in `.bc-agent/`); learning and knowledge keep the `.bc-agent/` vault. Hybrid adds the paths the hosted `teach` adapter maps. The visible layout has deterministic tests but has not yet been pressure-tested with a consuming agent.

## Design decisions

- **Visible layout for code, ops and hybrid (2026-11-12).** Provenance: the "Resolved decisions" of [the visible-layout plan](../../docs/plans/active/bc-init-agent-visible-layout.md), agreed with the owner; this is its work package W1. Knowledge is visible and `.bc-agent/` holds agent mechanics only (`AGENTS.md`, `map.md`, `log.md`, `conventions/`, `references/`, `templates/`). Work items move through `work/1-planned/`, `2-active/`, `3-done/<year>-<month>/`, `4-dropped/`; the folder is the status, so the work-item template has `Why:`, `Done when:`, optional `Issue:`, `## Steps`, `## Outcome` and no `Status:`. Ideas are lines in `work/0-ideas.md`; a plan is a work item, so no plan template or plans folder is generated. Decisions and research live in `docs/decisions/` and `docs/research/`; empty folders carry `.gitkeep`, and the four `work/` stage folders keep theirs permanently so every stage stays in git when empty. `docs/PRD.md`, `ARCHITECTURE.md` and `.agents/skills/` are named in the table and created on first need, not as placeholders. `tasks/`, `project/`, `decisions/`, `research/`, `scratch/`, `out-of-scope/`, `index.md`, `home.md`, Obsidian settings and `conventions/planning-workflow.md` are no longer generated for these archetypes.
- **Ops keeps its operational knowledge.** `docs/components/` with the `component` and `finding` templates; findings go to `docs/research/`, plans are work items.
- **Open questions are work, not a folder (owner decision 2026-11-12).** Ops and hybrid no longer generate `docs/open-questions/` or an open-question template. The generated `.bc-agent/AGENTS.md` of every visible-layout archetype says, with the work-item rules: a question that blocks a piece of work is a step in that work item; a standalone question someone must investigate is a planned work item whose answer lands in `docs/research/`; one not worth an item yet is a line in `work/0-ideas.md`. Why: `work/` stays the single place that shows what is pending.
- **Hybrid = ops layout plus exactly the teach adapter's mapped paths** under `.bc-agent/` (`learning/`, `sources/`, `concepts/` with `entities/` and `syntheses/`, `questions/`, `sessions/`, `references/teach-skill.md`, `references/teach-resources.md`, `templates/learning-session.md`, `index.md` as the teach catalog). Why: `teach` pins those paths, and changing them belongs to the teach redesign.
- **Hybrid has one glossary (owner decision 2026-11-12).** The hybrid adapter maps `teach`'s Glossary to the project's root `glossary.md` (`../glossary.md` from `<teach-root>`), shared with the project: `teach` adds and refines the terms the learner needs in the file's one-line format and does not remove or redefine project terms without asking; `domain-modeling` and planning skills keep using the same file. Hybrid no longer generates `.bc-agent/project/overview.md`, and `.bc-agent/project` counts as earlier layout for hybrid as for code and ops. `is_valid_teach_adapter` accepts exactly two maps, the vault map and the hybrid map, which differ only in the Glossary row; the learning archetype keeps the vault map. Provenance: resolved decisions of [the visible-layout plan](../../docs/plans/active/bc-init-agent-visible-layout.md).
- **Learning and knowledge keep the vault, byte-identical to before.** Why: `teach` reads exact vault paths and its tests pin them. `tests/test_visible_layout.py` compares their output with the scaffold at `e27f2e6`.
- **Existing projects are not migrated by the scaffold, and are refused by default.** On a project with earlier-layout paths under `.bc-agent/`, a visible-layout run writes nothing, names the paths and exits non-zero; `--allow-earlier-layout` creates the missing files beside the old ones instead. Why: two sets of homes for the same knowledge would both look current, and plan Q22 moves a project deliberately in one pass. See [MIGRATIONS.md](MIGRATIONS.md#visible-layout).
- **`--force` stays inside `.bc-agent/`.** Root `glossary.md`, `work/` and `docs/` hold the project's own content and are never overwritten; root `AGENTS.md` needs `--force-root`.
- **Generated text redirects skill defaults to the table.** `.bc-agent/AGENTS.md` tells agents to use the table's path when a shared skill names its own default (for example `docs/adr/`), and root `AGENTS.md` keeps `codebase-docs` off the table's record paths. Why: shared skills are written for several layouts, and until the consumer skills read the table (W3) this rule is the only redirect.

- **W3 review fixes (2026-11-12).** A large work item's folder holds `plan.md` (its `## Steps` are the slices) and `requirements.md`, plus any evidence; no separate slice files, because the steps already are the slice map (decision 10 refined in review, pending the owner's confirmation; recorded in the plan). The visible runway page keeps the default `docs/research` and `docs work` in its snippet and tells the agent to substitute the table's research and work paths when the project changed them. The map upgrade note fires only for an inline-code bullet whose target is an existing file inside `.bc-agent/`, so a bullet naming a project file created on first need (for example `docs/PRD.md`) is not flagged. Standalone teach state is matched by exact directory-entry name, so a hybrid project's shared root `glossary.md` is not mistaken for `GLOSSARY.md` on a case-insensitive filesystem. Provenance: the W2/W3 review of [the visible-layout plan](../../docs/plans/active/bc-init-agent-visible-layout.md).

## Interface: the "Where things go" table

Later work packages and other skills read project paths through this contract, not by assuming them.

- **Location and heading.** `.bc-agent/AGENTS.md`, section `## Where things go`.
- **Columns.** A Markdown table with header `| Role | Path | Notes |`. Path is a backticked path relative to the project root, or `—` when the role has no decided path. Notes say, among other things, "created on first need" for a path that may not exist yet.
- **Role keys** (`LAYOUT_ROLES` in [`body/scaffold.py`](body/scaffold.py)): `work-planned`, `work-active`, `work-done`, `work-dropped`, `ideas`, `decisions`, `research`, `glossary`, `requirements`, `architecture`, `project-skills`, `project-agents`. Ops and hybrid add `components`; hybrid adds `teach-workspace`.
- **Parser.** `parse_where_things_go(text)` in `body/scaffold.py` returns `{role: path}`. A backticked path is unwrapped; a plain path is returned stripped; only `—`, `-` or an empty cell maps to `""` (undecided). The heading must be a whole line (trailing spaces and CRLF tolerated; `### Where things go` does not count). It raises `ValueError` when the heading is missing, when the section has no table rows, or when a role appears twice. `where_things_go_table(archetype)` writes the table from `layout_rows(archetype)`.

## Open items

- **`project-agents` is undecided.** Its row has no path; the plan's open check is which project folder `pi-subagents` discovers agent definitions in.
- **qmd registration and the nightly `bc-wiki-maintain` timer** (Process steps 9 and 10) apply to learning and knowledge only for now. Why: both expect a vault with an index, which visible-layout projects no longer have; a later work package revisits them.
- **Merge is held.** The deploy symlinks point into `body/`, so merging this concept to the main checkout makes it live immediately. The merge waits until the consumer skills (W3) read the "Where things go" table.
- **Pressure test.** The skill's visible-layout process steps (PRD question, location suggestion, sync-folder warning, earlier-layout refusal) have not been run against a consuming agent; [tests/scenario.md](tests/scenario.md) checks 8a–8d are the packet.

- **Recon before grilling, then scaffold.** The skill now treats initialization as adaptive onboarding rather than blind file generation: inspect git/GitHub state, project shape, docs, build/deploy markers, and risk signals first; summarize what was found; then grill only the missing decisions. Empty folders get project-intent questions, active projects get integration questions, operational/system folders get component/evidence questions, learning folders get `teach`/learning-plan questions, knowledge folders get raw/source/entity/concept questions, and old/messy projects get reconciliation/migration questions before anything is written.
- **Wiki archetypes from real user patterns.** The scaffold recognizes `code` (project execution: work items, decision records, research including architecture reviews, references), `ops` (system operations: code plus components; open questions are work items), `learning` (teach-backed study vaults), `knowledge` (immutable raw sources → compiled source/entity/concept/synthesis wiki), and `hybrid` when a repo needs more than one durable mode.
- **Modes keep init from becoming magical.** The skill distinguishes recon-only, plan-init, apply-scaffold, and migration-assist modes. The deterministic scaffold remains additive; moving or copying existing docs into the workspace is a separate, explicitly approved migration step.
- **Deterministic scaffolding via a script.** File-tree generation from a fixed template is exactly the kind of thing an LLM does unreliably, so `body/scaffold.py` writes the base tree with `__SLUG__`/`__DATE__` substitution and optional archetype seed files via `--archetype code|ops|learning|knowledge|hybrid`. The skill body handles what needs judgment: environment recon, archetype selection, targeted grilling, plan proposal, the clobber guard's follow-up, conservative seed edits, the publish.yaml offer, and the commit. (AGENTS.md "scripts for anything an LLM does unreliably".)
- **Architecture runway nudges by a computed Git-history signal, not calendar time.** Code, ops and hybrid include `conventions/architecture-runway.md`, which counts commits touching the durable project surfaces since the last commit naming an architecture review and asks agents to nudge for `/improve-codebase-architecture` when that count reaches its threshold or structural friction appears. This remains advisory and only applies when the skill is present in the repo-local skill map.
- **Additive idempotency (never destructive).** The script creates only the files that are missing and leaves every existing file untouched; re-running changes nothing, and it **never deletes** (only `mkdir` + `write_text`, gated on non-existence). This makes it safe to re-run and safe to plug into an existing project — an existing root `AGENTS.md` or any pre-existing vault page is preserved verbatim (the existing root `AGENTS.md` is flagged for a manual pointer-merge). Overwriting is opt-in only: `--force` for files under `.bc-agent/`, `--force-root` for the root `AGENTS.md`; `--dry-run` previews. When an existing instruction file needs a pointer to a newly added scaffold file, the script prints upgrade notes for the running agent to merge by hand instead of overwriting. Chosen over the original "refuse if the vault exists" guard because that blocked the realistic case (dropping the workspace into a repo that already has some of these files).
- **publish.yaml: offer-then-confirm (user's choice).** The skill drafts a repo-specific allow rule following the existing publish-policy schema and offers to append it to `~/.config/agent-concepts/publish.yaml` after the user confirms; it never pushes that change (self-amendment immunity). This closes the loop with `bc-drain-issues`, whose preflight needs the repo authorized for AFK push and claim-branch coordination.
- **Map links participate in maintenance (2026-08-31).** The generated `map.md` uses real relative Markdown links for every target inside the vault, so `bc-wiki-maintain`'s existing `links()` parser and resolver can validate and count those graph edges. Future map entries follow the same in-vault-only rule; external source-tree references remain inline code because they cannot enter this vault's graph and would otherwise create broken-link findings. Existing maps remain untouched by the additive scaffold and receive an upgrade note instead.
- **One-time map migration stays outside the injected body.** The existing-vault procedure lives in [`MIGRATIONS.md`](MIGRATIONS.md), where a future maintainer can find it without loading a one-time operation into every initialized agent session.
- **Planning intent trigger.** The root/vault instructions now tell agents to ask whether to enter `/bc-plan-to-issues` when the human sounds like they are planning codebase work, and to offer `/improve-codebase-architecture` first for architecture runway. Concrete edit/fix requests still proceed normally.
- **Research vs actual PRDs (learning/knowledge vault).** The generated workflow distinguishes exploratory research/evidence (`research/`) from plans/PRDs that were actually drafted or published (`project/` / parent issues), so architecture reports and investigations do not get mislabeled as PRDs.
- **qmd registration by default at close-out, opt-out (replaced the short-lived `--qmd` scaffold flag, 2026-07-13).** The scaffold itself is qmd-free — no flag, no generated `references/qmd.md`, nothing per-repo (project-local `.qmd/` indexes shadow the global registry and can't be committed; see `concepts/qmd/`). Instead the skill's close-out appends the new vault to the synced global canon (`~/Sync/Scripts/config/qmd-collections.yml`) and runs `bc-qmd-setup`, asking only whether the user wants the vault excluded. Default-on because the realistic failure is a vault silently never joining the index.
- **Wiki-maintain timer: offer-then-confirm (2026-08-29).** Close-out
  offers to copy the `bc-wiki-maintain` runner templates to
  slug-suffixed user units so promotion can run overnight from day one.
  Confirmed by the user as offer-then-install, not mention-only and not
  default-on. The scaffold stays timer-free. qmd refresh is not this
  timer. Provenance: `concepts/bc-wiki-maintain/body/runner/`.
- **TODO stubs, not invented facts.** `validation.md`, `file-layout.md`, `references/*`, and the glossary ship as explicit TODO stubs for the project's agents to fill — preserving epistemic honesty rather than fabricating project facts.
- **Teach integration is an explicit adapter, not a second tutor.** Learning and hybrid overlays
  emit `.bc-agent/references/teach-skill.md` with the approved mission/review/records/knowledge/
  glossary/session mapping (hybrid's glossary row names the shared root `glossary.md`). The initializer owns host schema/orientation; teach owns pedagogy,
  evidence, and SRS state. Hybrid learning/knowledge overlays keep raw and compiled material in
  the mapped `sources/` and `concepts/` homes (entity/synthesis subtrees live below `concepts/`)
  rather than generating parallel `raw/` or `wiki/` trees. Existing standalone teach files remain
  in place, and any competing homes are reported for a user decision rather than migrated. A host
  choice alone never migrates state; teach's separate explicit migration operation is destructive,
  warns that originals will be deleted, verifies every destination first, and preserves originals
  when verification fails.
