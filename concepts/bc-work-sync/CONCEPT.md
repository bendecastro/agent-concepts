# Concept: bc-work-sync

Owner-started skill (`disable-model-invocation: true`) that brings a visible-layout project's `work/` folder in line with its own docs. It reads the docs the "Where things go" table names (requirements, decisions, research, ideas) plus open GitHub issues when the project uses them, shows the owner one plan, and writes items, moves, fixes and the regenerated index only after the owner answers.

## Design decisions

- **`Kind:` when the doc makes it clear (owner decision 2026-11-24).** Items created from docs get a `Kind:` line only when the source makes the kind clear, and are placed where `work_index.py --check` says: placement by kind, not by skill, below the existing top group so new items cannot flood ahead of the owner's.
All agreed with the owner on 2026-11-16.

- **Plan first, one plan, nothing written before the answer.** Why: a written item looks decided; the plan is where the owner catches a wrong stage, a duplicate or a stale doc. "Skip the plan" does not lift the gate.
- **Sources are the project's own docs only**, found through the table, plus open issues. Code TODOs, session notes and git history are not sources for discovering work; `git log` is allowed only to check existing items (landed work, last touched). Why: those record what someone once thought, not what the project decided.
- **Stages come from the project.** A `Stages:` line in `.bc-agent/AGENTS.md` lists them in order (default `now, next, later, unscheduled`), and every open item has a `Stage:` line directly under `Done when:`. The table in `work/README.md` is generated by bc-init-agent's `work_index.py`, which this skill runs and checks; the skill does not carry its own copy. Every open item also has a `Blocked by:` line (owner decision 2026-11-22); the plan reports items without one and blockers naming unknown, dropped or self items or forming a cycle, and proposes the "Blocked by" migration when no item has the line.
- **Docs win; docs that disagree with each other are the owner's call; the decision log is append-only.** A requirements doc that looks stale against a newer decision is a question, never a pick.
- **Docs refer to items by number** ("work item 012"); only the generated README links paths. Why: a path breaks each time the item changes status folder.
- **After approval:** write under the project's template and work-item rules (numbers only in the main checkout, links instead of copied content), regenerate and check the index, commit, independent review, fixes, then run the owner's publish check, `python3 "$AGENT_CONCEPTS/scripts/publish-check.py" --repo "$PWD" --remote "$(git remote get-url origin)" --branch "$(git branch --show-current)"`, and check the matched rule's `when:` conditions. If the check is unavailable or no rule matches, ask; do not restate the policy.
- **The plan format is a separate file** ([body/PLAN.md](body/PLAN.md)) so `SKILL.md` stays short.

## Provenance

- The 2026-11-16 tidy-up of one of the owner's projects' work pipeline, done with the owner: its `work/README.md` table, its work-index script (ported to bc-init-agent's `body/work_index.py`), the `Stage:` rule in its `.bc-agent/AGENTS.md`, and the owner's decisions about sources, conflicts and the plan gate recorded above.
- Gate phrasing adapted from [bc-prompting-agents](../bc-prompting-agents/body/SKILL.md) (Scope discipline and Loading is not authorization). The gate deliberately ends the turn on a plan.
- Work-item rules (status folders, numbering in the main checkout, ideas file) from the scaffold in [bc-init-agent](../bc-init-agent/CONCEPT.md).
