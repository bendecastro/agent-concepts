# Concept: tdd

Model-invoked discipline for test-driven development: a red-green-refactor loop that builds features or fixes bugs one vertical slice at a time, testing behavior through public interfaces. The correctness feedback loop that lets an agent run human-in-the-loop or unattended without drifting silently.

## Design decisions

- **No links into other concepts (2026-11-25).** Installers copy each skill alone, so the body states inline the parts of the kernel's Storage safety rules it relies on and names `agent-kernel` as optional extra context instead of linking into its folder. Since 2026-11-28 (item 054-safe-runs-module) those storage and worktree-removal rules live in `bc-safe-runs`, which the body loads by name; the body keeps one fallback line.

- **Test layout norms (2026-11-19).** Browser/integration tests only for behaviour a fake cannot show; each file builds its own state; files under about 25 tests or 60 s; parallel runner and `slow` marker from the first test commit. Each rule carries a time Why. Source: the agent-time-sinks council memo (2026-11-19: worker e2e and pasted full gates dominated agent wait time in project A) and the owner's decisions of that date. `bc-code-review` checks them on new test files (same change). Other tdd consumers (bc-pipeline-to-done, bc-executing-plans, bc-subagent-driven-development) load tdd for authoring and pick the section up unchanged; no consumer contract changed.
- **Broad invocation.** Test edits, bug fixes and features with tests trigger the discipline even when tests are incidental; opt-in test-first wording missed ordinary work.
- **Unattended planning.** Delegated/headless agents record behavior priorities and interface decisions rather than waiting for unavailable approval; interactive approval remains unchanged.
- **Tests after code still need RED.** Coverage/regression/characterisation additions require a watched behavioral failure and restored green, recording both runs.
- **Inject inline boundaries.** A keyword boundary parameter with the real default preserves behavior while exercising owned helpers; out-of-scope seam changes are reported, not replaced with internal patches.
- **Confirm old-code RED.** The stdlib archive-and-overlay CLI isolates current changed tests from current production code without touching the user's Git state. Missing-symbol failures warn rather than claim behavioral sufficiency; unchanged production requires a manual mutation.

- **Tests that lie.** Merge the talk’s three classes into the existing internal-mock refusals. A sampled, read-only audit found private-helper patches/call assertions dominant in orchestrator tests (roughly 25–40% in one sample, not a census); use boundary fakes, public entry points and independent oracles instead. The per-test regression self-check sharpens the existing RED step, not a new result state.

- **Behavior-through-interface is the core rule.** Tests verify what the system does via public APIs, not how it does it internally. The named anti-test is the implementation-detail test (mocks internal collaborators, asserts call counts, breaks on refactor without behavior change). Detail in `body/tests.md`.
- **Vertical, not horizontal.** "Write all tests, then all code" is the explicit anti-pattern — bulk tests assert imagined behavior and the shape of things. One test → one implementation → repeat, each cycle informed by the last. Shared framing with `bc-to-tickets` tracer bullets.
- **Mock only at system boundaries.** `body/mocking.md` draws the line: external APIs/DB/time/FS yes; your own collaborators no — via dependency injection and SDK-style interfaces.
- **Never refactor while RED.** Refactoring is safe only with a green test as the safety net; `body/refactoring.md` lists candidates.
- **Pressure-refusal gates (2026-07-16).** Horizontal-slice, call-count, mock-internal, and refactor-while-red each get an explicit refuse-under-pressure clause after the 2026-06-21 FAIL (agent named the anti-pattern and still committed it).
- **Composes `bc-codebase-design`.** Planning step reaches for the deep-module vocabulary and testability checks rather than restating them.
- **Progressive disclosure.** Lean `SKILL.md`; `tests.md` / `mocking.md` / `refactoring.md` loaded only when that depth is needed. (Upstream's `refactoring.md` was recovered as a summary; reconstructed faithfully — see provenance.)
- **`untested` as a TDD result state considered and rejected (2026-09-06).** A review findings table needs a third state because a skipped check and an inapplicable one look identical. A TDD cycle does not: its states are exhaustive (the test exists and fails, or exists and passes). A third "result" would become a sanctioned route past RED and would defeat "watch it fail for the right reason." The blocked case — no runner, missing fixture, unbuildable environment — is a stop-and-report, not a result value.

- **Standard-library boundary patches allowed (2026-11-05).** Patching `subprocess.run` or `urlopen`, even via the module under test (`patch('tags.subprocess.run')`), fakes the external call; replacing the module's own functions/helpers/classes is what is forbidden. Owner decision after a kernel-only run graded such patches as failures under a too-strict criterion; injection stays preferred when tests need several patches.
- **Assertion scope and small fixes (2026-11-05)** — watched-fail and planning rules cover new tests or behaviour-changing assertions, not mechanical test maintenance. Explicit regression-test bug-fix wording preserves discovery without making tdd the diagnosis owner; bc-diagnosing-bugs still owns unclear repros. Small, clear fixes skip interactive plan approval, not RED/GREEN. Drain feature workers retain the same red-green loop; bc-code-review’s tests-that-lie definitions and both outgoing storage/glossary contracts are unchanged. The kernel now loads tdd for this scope; fake-boundary details have one home here.

- **Three test levels (2026-11-17).** Owner-approved model. Level 1 examples are unchanged. Level 2 property-based tests are required for logic with a statable rule (parsers/formatters, transforms, calculations, sorting/filtering, state transitions) and optional for glue, UI, I/O wiring and config, because examples only cover inputs the author thought of. Hypothesis, fast-check and proptest run inside the project's existing suite and command, so there is no new gate; the library becomes a dev dependency the first time a project needs one. Shell is excluded: rule-bearing shell logic moves to Python. Fail-first is kept, so a property on working code needs a planted-and-reverted mutation, recorded where validation is already reported (`bc-pipeline-to-done`' `validation.json`, otherwise the report) rather than in a new evidence file. Default example counts keep run cost predictable; shrunk failures are pinned as explicit examples because local caches (`.hypothesis/`) are gitignored machine-local state, added to a sync tool's ignore list only when the project is in a synced folder (made conditional 2026-11-27 after the stranger rerun's worker wrote a `.stignore` into an unsynced project). The agent writes properties and bc-code-review's Spec axis checks them; weakening or deleting one needs owner approval. No migration or backfill: a project's `validation.md` gains its entry when its first property lands. Level 3 formal verification is only a reserved, off-by-default, per-project slot; its rules wait for a pilot. Detail lives in `body/properties.md` to keep `SKILL.md` lean.
- **Level 3 rules (2026-11-17, owner decisions).** Level 3 is full proof only: Dafny for Python/JS/TS (prove, then compile to the target, because neither language has a mature full-proof verifier), Verus for Rust, TLA+ with TLC for designs (bounded models allowed for designs only) plus Apalache inductive invariants for rules that must hold in every state at fixed sizes; shell has none. Kani and CrossHair were excluded because bounded or symbolic search finds bugs without proving the rule. Only the owner turns it on, per component, with a fixed `Level 3: on` line in `validation.md`, because a proof is a standing cost. Agents must suggest it — a fixed `Level 3 candidate:` line — whenever a change touches a risk-class component (persisted data, money, security/permissions, concurrency/sync, a core calculation) that is neither on nor declined; a refusal is recorded as a dated `Level 3 declined:` line and suppresses re-suggestion until the risk class changes. Suggestions are mandatory because only the owner can turn proofs on, so an agent's silence removes the choice. The spec file pairs each plain-English rule with its formal statement plus an assumptions list: the owner approves the English and assumptions, an independent reviewer checks the formal match and escape hatches. Proofs run on every touching change and in final validation with a pinned tool; missing tool or timeout is `untested` and blocks only that component. Dafny output is committed, marked do-not-edit, checked by regeneration, and guarded by Level 2 properties at the hand-written boundary. Detail lives in `body/formal.md`.
- **Test levels block (2026-11-17, owner decision).** Every change report carries a fixed three-line `Test levels:` block (L1, L2, L3 with enumerated choices) so a skipped level is a visible claim the reviewer can check against the diff rather than a silent omission. `bc-code-review` audits it; `bc-pipeline-to-done`' gate (instruction-only, since the driver is a model) rejects a missing or empty block.
- **A work item's owner-marked `Dependencies:` line is a waiver (2026-11-27).** A line `bc-plan-to-pipeline` marked as the owner's answer counts as quoting the owner for skipping the property library; an unmarked line or an orchestrator's words do not. Why: planning already asked the owner, and the planned-dependencies pressure test saw every builder block on the item's answered line (`../bc-pipeline-to-done/tests/pressure-planned-dependencies-results-2026-11-27.md`).

- **Machine tools named by role, not by name (2026-11-19).** The storage check before `confirm-red.py` on a large repo and the property-test runner say "the machine's storage health check" and "the guarded runner, if the project or machine names one". Why: the repository is public; the owner's tool names already live in the owner's always-loaded instructions, so no overlay is needed.
