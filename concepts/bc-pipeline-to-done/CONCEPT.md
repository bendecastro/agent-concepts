# Concept: bc-pipeline-to-done

User-invoked AFK executor (renamed from `bc-drain-issues` 2026-11-25; the old name stays as a deploy alias) for a repo's ready queue from one of two sources: planned work items carrying `Ready for agent: yes`, or non-`automated` `ready-for-agent` and `rework-for-agent` GitHub issues. A preflight-gated driver claims dependency-ready units, gives fresh builders isolated worktrees, requires independent Spec + Standards approval, permits bounded same-worktree rework, and mechanically lands approved diffs. On the issue source it closes a parent PRD only after all children complete; on the work-item source it finishes the item after its last step. Runs after `bc-plan-to-pipeline`; `bc-` is the user's personal namespace.

## Design decisions

- **Regression checks are part of the fix (2026-11-27).** The driver includes `bc-performance-guardrails` in the packet rather than relying on the fresh worker to discover it. The builder reports the new check or a concrete reason no check can catch the regression; Spec reviews that evidence. Both arms added a check in the [bundle-size dry run](tests/pressure-regression-guardrails-results-2026-11-27.md); only the treatment loaded the skill and documented the cap.

- **Roles are required; machine helpers are not (2026-11-26).** Stop before claims, worktrees or baseline checks if the harness cannot supply fresh auditor, builder and reviewer jobs. Point Pi users to the extension or example profiles, rather than letting the driver fill in. Skip absent storage checks with one report line; keep configured-check failures blocking. Worker packets keep the temp-file rules when falling back to plain pytest.

- **No policy is distinct from policy denial.** The checker must report the missing file explicitly. The owner's yes sets single-driver mode and authorizes target-branch pushes for the current run without granting claim-ref or issue mutations. With nobody to ask, local-only mode keeps commits local and never writes remotely. Policy-based authorization and self-amendment immunity still apply.

- **No links into other concepts (2026-11-25).** Installers copy each skill alone, so the body states inline the parts of the kernel's Storage safety rules it relies on and names `agent-kernel` as optional extra context instead of linking into its folder. Other skills are named, not linked (`bc-tdd`, section Test levels and friends), with a `loads` edge.

- **One skill, two sources; the shared rules exist once (2026-11-25, owner grill).** Renamed from `bc-drain-issues` because the loop's third step must also build work-item projects. `SKILL.md` is the shared core (claim protocol, packets, review, landing, recovery, safety) written for a unit of work; `source-issues.md` holds everything GitHub-specific, moved verbatim so issue behaviour is unchanged; `source-work-items.md` is the work-item source. The core keeps the issue claim key `issue-<n>` in its protocol lines and says to read it as the chosen source's key, so the Gate A string checks on the claim protocol stay exact. `execute-issue.md`, `review-contract.md` and `recovery-bundle.md` keep their issue wording under the same reading rule rather than being rewritten: a rename would only churn links. Gate A now reads `SKILL.md` plus `source-issues.md` as the issue rules. The old name stays a deploy alias so habits and links keep working.
- **Jobs, not role names (2026-11-25, owner grill).** The body names three jobs and their limits (each fresh, without the broad skill catalog, given only the skills the contract passes; auditor: read-only; builder: writes in its own worktree, never commits; reviewer: read-only, fresh) and reads `~/.config/agent-concepts/overlays/bc-pipeline-to-done.md`, when present, for which roles and models do each job. Why: the owner's live role files were links into this public repository, so their setup and the public examples could not differ, and a stranger was forced to copy fixed names. `body/examples/agents/` stays as optional examples whose names are examples (first shipped 2026-11-24 so a stranger could launch something); the owner's role files become their own copies. Gate A check 6 now audits these shipped examples against the job limits instead of the machine's role directory.
- **Work-item source (2026-11-25, owner grill).** Eligibility is the explicit `Ready for agent: yes` line plus done blockers plus pipeline order, because `Planned:` proves planning, not consent to run unattended. The claim unit is the whole item worked by one builder step by step, since steps share a worktree and an item's outcome. With a remote the item uses the issue claim ref keyed `item-<slug>`; without one, only a single driver may run and the committed move to work-active is the claim, because a folder move is not atomic across drivers. An item needing the owner is parked back in work-planned with a `Waiting on owner:` line and its ready line removed, and the question goes where the owner sees questions, so the dashboard shows what is waiting.
- **Fresh workers, durable packets, isolated worktrees.** The issue/Agent Brief, acceptance matrix, repository context, diff, findings, and validation artifacts—not a parent transcript—form the handoff. A remote `bc-drain-claims/issue-<n>` branch is the cross-run ownership lock: no-force creation when absent, exact-lease fast-forward acquisition from a valid Released Claim Marker; labels are advisory. Worktrees outside the main checkout provide filesystem isolation.
- **Released Claim Markers (2026-10-04).** Adopt project B ADR-0041's exact subject/body/parent format so cloud releases do not strand the local queue. Validate the issue/ref and claim/parent identity before treating a marker as free; malformed or unreadable tips remain held/unaccounted. Acquisition needs both a reported ref update and remote SHA equality, and local deletion remains the default release with exact-lease marker cleanup permitted. Worker/review/recovery contracts still forbid worker claims and require safe capture before release; no review or recovery semantics change. The TDD loading edge and planner handoff are unaffected; generated initializer guidance now points to this claim protocol instead of assuming every claim creates an absent ref.
- **Owner/cloud lane isolation (2026-10-04).** `automated` is the repo's cloud-lane provenance label, excluded from fresh/deferred/rework selection and restart recovery before any claim/label mutation. Cloud-build may consume both owner and automated issues, so a shared claim ref is not proof of local ownership: report active automated claims, including `in-progress-agent` without a ref, and never release/delete/reuse/relabel them as untouched or abandoned work. Leave pre-existing in-flight local bundles unchanged, with no migration/deletion. Structural marker/CAS fences, absent-ref creation, owned-claim release, non-automated attended landing, and review remain unchanged. Relationship accounting: the outgoing TDD load in `execute-issue.md` still governs eligible feature workers; the incoming optional planner recommendation still hands off a queue, not guaranteed selection of every issue; `bc-setup-project/body/scaffold.py`'s **Claim before work** bullet already says to follow the drain's authorized protocol, so it consumes this gate without a duplicated selector or any change to its absent-ref/marker lease guidance. No relationship edge changes.
- **Cloud-claim provenance extends the cloud lane (2026-10-08, corrected round 2).** Owner cloud-build also claims OWNER issues with no `automated` label (project B issue #300 item 5; live #361 held `bc-drain-claims/issue-361` with `branch=cloud-build/issue-361` plus a `cloud-build-run` comment): a non-`automated` issue is cloud-lane work — skipped, reported, never released/deleted/reused/relabelled, exactly like `automated` — when any of: its held non-marker claim tip names `branch=cloud-build/issue-<n>`; it carries `in-progress-agent` with a `cloud-build-run` comment; it has an open PR from `cloud-build/issue-<n>`. A lone `cloud-build-run` comment with a released-marker/absent ref, no `in-progress-agent`, and no open cloud PR is history and follows the normal owner path (round-1 text wrongly made every `cloud-build-run` comment live, which would have starved the released-claim owner path). Labels first, then read-only tip, then comments/PRs, before any recovery disposition or mutation; single specific fail-closed on labels/tip/comments/PRs; untouched never applies to a cloud-lane claim. A valid Released Claim Marker tip is still FREE, but an open cloud PR or `in-progress-agent` with a `cloud-build-run` comment stays cloud-lane for selection. Relationship accounting: no edge changes — outgoing TDD load, incoming planner handoff, and `bc-setup-project/body/scaffold.py` Claim-before-work delegation are unchanged (checked `RELATIONSHIPS.md` and scaffold guidance).
- **Compatibility alias retired (2026-09-27).** `/implement` was removed as an alias; use `/bc-pipeline-to-done` for this executor.
- **Preflight preserves publish and queue safety.** Branch/remote cleanliness, `publish-check.py`, claim authorization, label availability (including `rework-for-agent`), GitHub/PRD access, worktree/recovery roots, qmd mode, and caps are checked before AFK launch. The drain never self-authorizes. Dependencies from bodies/comments must be closed and unclaimed before dispatch.
- **Risk controls are proportional.** Ordinary slices use explicitly medium effort. Compatibility replacement/retirement, migration/cutover, systemd/external-service semantics, and broad public surfaces use high effort plus a bounded read-only contract audit. Raised from low/medium on 2026-09-30 at the user's direction, keeping one step between ordinary and high-risk slices. Replacement audits inventory the entire old public interface from source/tests/help and map requirements to evidence. Material external-platform claims are checked against available primary docs/help rather than trusted from repository prose; narrow new-command and string-presence tests previously missed costly compatibility defects.
- **The contract audit inventories guards, not only interfaces (2026-07-27).** Added a `guard/rejection clause -> can-its-inputs-differ-in-production evidence` row after a real drain of an inert-guard issue reproduced the very defect it was fixing: the worker deleted the named tautological clause and left a sibling clause tautological, then made it *harder* to see by substituting an expression with an identical runtime value. Independent Spec review caught it, but the audit is the cheaper place — it runs before implementation. The row is mandatory for every guard a guard-issue's diff touches, keeps, or relocates, because fixing one member of the class while leaving another is the observed failure. Recorded in `review-contract.md` too, since a driver-materialized packet is the only instruction an AFK reviewer sees.
- **Cached baseline, targeted editing checks, final full validation.** Full project validation runs once per base SHA for a baseline and once before landing. Editing/rework/review use targeted evidence and baseline deltas. This retains regression detection while avoiding repeated full-suite cost.
- **Deterministic gate before lean independent review.** The driver mechanically checks acceptance coverage, status/diff scope, targeted validation/baseline delta, no staged/unrelated files, and external evidence before spending model review. Fresh read-only agents get minimal packets and strict compact JSON; the packet is authoritative, so generic absent `plan.md`/`progress.md` conventions cannot block them. They never run the full suite.
- **The driver materializes the review packet; reviewers never re-derive it (2026-07-26).** Diff, changed-file list, matrix, and validation are written once per round outside every worktree, and reviewers read those paths instead of re-running `git status`/`git diff`. Independence is a property of reasoning, not of repeating the driver's deterministic Git work. The packet's `diff_sha256` and acceptance-matrix→file map also supply the identity and mapping that standing approvals and invalidation triggers need, so one artifact serves economy, determinism, and auditability.
- **Standing approvals with deterministic invalidation supersede re-reviewing every axis every round (2026-07-26).** An approval binds to the exact diff hash it examined. After a rework round the raising axis always re-reviews; an approving axis re-reviews only when a driver-computed trigger fires on the delta, and an unmappable delta invalidates both. Before landing, every axis must hold a standing approval matching the final diff hash, so "both axes approved the landed diff" stays literally true while the same question is not paid for twice. This generalizes the pre-existing rule that a rebase changing the reviewed diff invalidates approval.
- **Review tiers make axis count proportional to risk (2026-07-26).** High-risk slices and any diff touching a public interface, security/privilege boundary, or installed/launcher topology keep two independent axes. Ordinary slices get one combined reviewer that works both scopes. This is the only economy control that genuinely trades independence, so it is bounded by one-way escalation: a pre-review gate rejection or any Critical finding moves the issue to tier 2 permanently, and tier plus reason are reported per issue for human audit.
- **Rework re-evidences a narrowed scope with carry-forward (2026-07-26).** v2 stopped the reworker rebuilding from scratch but still made it repeat the full review-ready gate each round: re-map every acceptance row, re-run targeted validation broadly, re-inspect the whole diff. The reworker is the priciest unit after the initial build (Gate B: 50,425) and is paid up to three times, so that repetition dominated contested issues. It now re-evidences only the rows implicated by the findings, the rows whose mapped files its fix touched, and anything already failing or flaky; other evidence carries forward. Full-scope status/staged/unrelated inspection is dropped entirely because the driver's deterministic gate re-checks it immediately afterward. This mirrors standing approval on the review side—carried-forward evidence with deterministic, driver-verified invalidation—so one matrix→file map serves both. **Accepted trade-off:** a fix breaking an untouched, unimplicated row is now caught by the driver's final full validation rather than mid-round, which wastes that round's review tokens but cannot land a regression, because final full validation still gates the commit. The touched-row rule and the always-rerun failing/flaky set cover the common cases.
- **Reproduction is gated on a formed finding (2026-07-26).** "Bounded targeted reproduction" read as licence for exploratory command runs. A reviewer may now run commands only after naming a candidate Critical/Important finding, at most two per finding, purely to prove or refute it. Refuted hypotheses are dropped silently.
- **Deployment Gate B uses a deterministic trace; natural contest remains ecological pressure (2026-07-27).** Autonomous model discovery could not reliably produce the two Standards-only reworks needed to measure selective re-review: the preserved natural v2 attempt stopped after one. The deployment benchmark therefore locks S0 → S1 → S2 and v2/v3 dispatch topology while keeping reviewer JSON, reworker patches, Pi lifecycle usage, and correctness real and independently verified. Golden transitions preserve comparable topology; model mismatch fails fidelity rather than changing rounds. Because Spec skips the two intermediate v3 rounds, its S0 hash cannot land and one focused S2 Spec hash-sync is mandatory.
- **Bounded same-worktree rework supersedes one remediation (2026-07-25).** Initial review may be followed by up to three fresh compact rework/re-review cycles. Continue only on material progress; the same unresolved finding after two attempted fixes defers. Minor findings do not block. Issue #29 showed the former second-finding terminal policy discarded useful fixable work rather than increasing safety.
- **Fresh reworker narrowly supersedes the rejected separate-fixer decision (2026-07-25).** A reworker does not reconstruct the issue from scratch: it receives the existing worktree, acceptance matrix, unresolved findings, and validation evidence. This keeps TDD artifacts and breaks self-review bias without replaying an ever-growing implementation context.
- **Fixable is not human-blocked.** `HUMAN_BLOCKED` is only for decisions, access/resources, ambiguous contracts, or irreparable environment failures. Round-limit or no-progress exhaustion becomes `REWORK_DEFERRED` with `rework-for-agent`, a validated machine-local recovery bundle, and a portable Agent Rework Brief. Repeated infrastructure failure is `SYSTEMIC_FAILURE`.
- **`HUMAN_BLOCKED` comments are for the human who will unblock (2026-08-18).** Decision or missing access first, options and consequences, then exact evidence. SHAs/paths/commands stay literal. A thin utterance clause, not a `bc-plain-language` load — workers still return `BLOCKED_NEEDS_HUMAN` with evidence; only the driver's GitHub comment is human-facing. The final stop-and-report and Agent Rework Brief stay mixed/agent-facing and were deliberately left alone.
- **Recovery is exact and fail-safe.** A versioned bundle records a binary-safe tracked patch, safe untracked regular files, acceptance matrix, findings, validation evidence, identities, hashes, and exclusions. Exact matching-base identity uses a canonical temporary-index Git tree OID rather than tar metadata or an improvised diff hash. Ignored/cache/secret/unsafe/out-of-scope content is forbidden. Changed-base restore requires three-way application, entire-diff inspection, validation, and full re-review. Failure preserves evidence and routes safely rather than guessing.
- **Child-token circuits were removed; correctness and bounded progress remain.** Per the user's 2026-09-26 decision, child-token totals no longer narrow review, defer otherwise review-ready work, or stop issue launches. The current bounds are `max-iters`, `max-parallel`, an initial review plus at most three rework/re-review cycles, and deferral when the same unresolved material finding survives two attempted fixes. Round/no-progress deferrals still require validated recovery; repeated tooling/base/environment failure still stops launches as `SYSTEMIC_FAILURE`. The former 200k/300k limits and two-token-deferral stop are historical policy, not current controls.
- **The chat report prices children, it does not count tokens (2026-08-24).** A Homeflix drain showed last-turn `totalTokens` and input/output/cache splits as noise: cache dominated the count while Luna and Grok tokens were not comparable. The stop report now lists each dispatched child as role + launched model/thinking + list-API dollars, then one child-run total. Price from summed harness per-call `cost.total` or published rates; `$unavailable` beats an invented figure. Child-token totals are not a run-control or report metric. The driver session is not a child row.
- **Driver owns landing.** Workers own code/tests/validation and never commit, push, close, label, claim, or clean. After both reviews approve, the driver inspects the reviewed diff, performs the final full validation, commits only issue work, rechecks publication, pushes `HEAD:master`, closes with evidence, and releases resources. A rebase that changes the reviewed diff invalidates approval and requires validation plus focused fresh dual review.
- **PRD closeout and recurring-defect tune remain global.** Only the driver can see all children and close a completed parent. Failure shapes recurring at least twice may additively patch later run-local packets, never canon or gates; patches/triggers are reported for later user promotion.
- **Post-landing architecture observations are optional and bounded (2026-08-20).** After a successful landing, the driver may emit at most one `architecture_observation` per issue, or none for an ordinary issue with no structural signal, shape-only taste, or deferred/blocked/abandoned work. Eligibility is concrete structural friction that survives the deletion test or leaves behavior untestable through an interface. The exact fields are `source`, `module`, `interface_or_seam`, `friction`, `deletion_test`, `evidence`, and `status: open`; `source` names the landed issue/commit and current tree. The observation uses `module` / `interface` / `seam` / `depth` vocabulary where applicable, records evidence and the deletion-test consequence, and contains no proposed refactor, interface design, or implementation direction.
- **The observation is a declared project-context update, not drain authority (2026-08-20).** For a scaffolded project, resolve `.bc-agent/research/architecture-observations.md`; otherwise use only an equivalent inbox path explicitly declared by project instructions. After the implementation commit lands, write each new entry by prepending it in the consumer's current newest-first order, so bounded reads cannot hide new observations below older history. Keep it as a separate driver-owned context-only update and report the inbox path plus context commit, or `not persisted` and the missing/unwritable reason. An explicit handoff carries only the observation into the report/context copy: it stays outside the implementation diff and review packet and cannot dispatch a child or change review authority, review/rework dispatches, tier, approvals, dispatch topology, landing, labels, or issue state.
- **Visible-layout projects: role lookup, work items, ideas sink (2026-11-12).** The body resolves the work-planned, work-active, work-done and ideas roles in the project's "Where things go" table (`.bc-agent/AGENTS.md`). With a table, the driver's landing commit also checks the issue's step in its work item and `git mv`s the item to work-active, or to the work-done `<year>-<month>/` folder with `## Outcome` filled when the landing completes it; it never writes a `Status:` line or a live-cursor page. This is the only content in the landing commit outside the reviewed diff; same-commit was chosen over a separate bookkeeping commit because decision 16 binds the move to the work and a separate commit leaves the tree showing finished work as active. Issues stay the drain's queue and optional pointers (`Issue:` line, or a step in a large item's `plan.md`); an item without an issue is not drained. A worktree worker never creates a numbered item and never edits the ideas file: it lists follow-ups as one-line entries in its handoff, and the driver, in the main checkout, appends them to the ideas file after landing in the same separate context-only commit as the architecture observation (W3 review, 2026-11-12: the line is outside the issue's scope, so the scope gate or reviewer would reject it, and parallel workers appending to one file conflict). The architecture observation goes to the ideas file as one appended line, since the visible layout retires the separate inbox. A landed issue that no item names changes no work file and is reported as "no work item"; a completed item's `## Outcome` cites issue numbers and earlier commits, not the landing commit's own SHA. Without a table nothing changes: no work items, and the `.bc-agent/research/architecture-observations.md` or declared inbox with newest-first prepend. The claim-before-work rule is stated in the body itself because visible-layout projects no longer generate `planning-workflow.md`, which carried the pointer. Provenance: decisions 2, 4, 10–16, 20 and 21 in [the bc-setup-project visible-layout plan](../../work/3-done/2026-11/018-bc-init-agent-visible-layout.md).
- **The inbox edge is distinct from the recurring-defect tune (2026-08-20).** The recurring-defect tune reacts to a failure shape recurring across at least two workers/reviews by patching later run-local dispatch packets; it is not durable architecture evidence and never edits canon. The observation is one post-landing, evidence-backed structural signal for the project's optional architecture-review inbox. Neither path changes the other.
- **TDD/diagnosis/autoresearch composition remains.** Feature work uses thin RED/GREEN/refactor increments; bug/performance work diagnoses from a red-capable reproduction; metric refinement occurs only after GREEN with correctness and objective improvement gates. Workers search a driver-refreshed qmd collection but never index it.
- **Agent-agnostic canon with concrete Pi economy.** State, packets, contracts, round caps, and recovery semantics work in any harness. Pi installs minimal `bc-drain-auditor`, `bc-drain-worker`, and `bc-drain-reviewer` roles with no unrelated inherited project context/skills or generic plan/progress reads, plus compact subagent tool descriptions. Other harnesses use equivalent fresh packets. Harness sessions/artifacts stay outside issue worktrees so metadata cannot fail scope gates or enter recovery bundles.
- **Test levels block in the pre-review gate (2026-11-17).** The deterministic gate rejects a handoff whose tdd Test levels block is missing or has an empty L1/L2/L3 line, so a skipped level surfaces before reviewer tokens are spent. The gate is instruction-only (the driver is a model; no gate code exists), so the check is added to the gate's checklist and the worker's review-ready checklist. Whether each line is true stays with the Spec reviewer: the gate checks presence, not judgment. Provenance: owner decision 7 of the Level 3 rules in [bc-tdd](../bc-tdd/CONCEPT.md).

- **The worker names no machine-specific test runner (2026-11-19).** `execute-issue.md` defers to the guarded runner the project's or machine's agent instructions name, as the kernel's Storage safety does, instead of a fixed command and owner path. Why: the repository is public, and a stranger's machine has its own runner or none; the owner's runner is already named in the owner's always-loaded instructions, so no overlay is needed.
- **Unplanned items are skipped (2026-11-24, owner decision).** With a table, an issue whose work item is still in work-planned without a `Planned:` line is skipped before claim and reported as "needs planning", with one note filed to the configured destination if usable. Both sources can park a work item using `Waiting on owner:` instead of requiring a question destination. On the issue source this leaves the issue unclaimed and preserves any existing waiting question. The drain does not run `bc-plan-to-pipeline` itself: that skill asks the owner questions and the drain is AFK, so nesting it would either stall the run or guess answers.

## Measured basis

These are historical measurements and design inputs; token totals are not current run controls. Gate B measured review at 61,012 of 277,012 child tokens (22%) on a *clean* v2 issue: Spec 24,104, Standards 36,908, one round, no re-review. The exposure is the multiplier rather than the single pass—an initial review plus three permitted rework cycles dispatches up to eight reviewer children, roughly 244k tokens at those rates, most of it re-reading a diff an axis already approved. v3 therefore attacks repetition (standing approvals, selective re-review), duplicated derivation (driver-materialized packet), disproportionate axis count (tiers), and ungated exploration (reproduction budget). Because clean and probabilistic single-rework fixtures cannot exercise selective re-review reliably, v3's deployment Gate B uses the deterministic two-rework trace; the natural contested fixture remains complementary ecological evidence.

Issue #29 recorded 16 child implementation/review runs totaling about 1.89M child tokens and $28.76 (parent excluded). Two failed drains spent about 621k tokens and discarded useful diffs; the later normal implementation spent about 1.27M more before landing. Review found real compatibility and systemd defects, so v2 preserves dual review while removing lost-work, broad-context, repeated-full-validation, and false-human-blocker costs. This evidence explicitly supersedes the old one-remediation limit and the broad rejection of a separate fixer.
- **Acceptance evidence must discriminate, not merely exist (2026-08-20).** The driver's deterministic gate proves every matrix row *has* evidence and that rework re-evidenced every touched row. Neither asks whether the evidence would look different had the criterion been false, so a row can carry a green test that passes for an unrelated reason and clear the gate. The rule went to the Spec reviewer rather than the driver gate deliberately: it is a judgment call, and putting it in the deterministic gate would break the one property that gate has. It is scoped to rows implicated by the reviewed diff so it cannot become a per-round full-matrix audit undoing the v3 review economy, and its remedy is discriminating evidence rather than more evidence so it cannot feed a remediation spiral. Deliberately phrased as a sibling of the unfireable-guard rule (*earns credit only once you know…*) so the two read as one family. Origin: the acceptance-mutation idea ingested from unclebob's Acceptance Pipeline Specification, whose own concept was removed as unusable here; this is the part of it that applies to a pipeline whose specs are prose checkboxes.
- **Solution sizing reaches the worker; deepening does not (2026-08-20).** `bc-minimal-solution-ladder` was deployed on the shared bus but never fired inside a drain: the Pi roles exclude the broad skill catalog by design, and the dispatch line named only `bc-tdd`, `bc-diagnosing-bugs`, and `bc-optimize-code`. Adding it to that list is the whole mechanism — no new phase. The user's original proposal was a **second builder** loaded with a contradictory shape skill, rejected on four counts: a second builder has no Agent Brief and its diff is scope creep by the Spec axis's own definition; rewriting matrix-mapped files fires the Spec invalidation trigger and pays build *and* review tokens twice under the then-current 200k soft cap and an unmeasured Gate B; depth is an interface decision made before the implementation exists, and `bc-tdd`'s refactor-while-GREEN is already the in-worker slot for shape; and architectural deepening already has a home one layer up in `bc-improve-codebase-architecture` → `bc-plan-to-pipeline`, where it arrives as its own slice with its own acceptance criteria. The ladder-vs-deep-modules contradiction the proposal assumed does not exist — it was arbitrated when the ladder was adapted (`bc-minimal-solution-ladder` CONCEPT.md, arbitration 1): the ladder governs *how much*, `bc-codebase-design` governs *what shape*, and both were loaded into one worker rather than split across two.
- **Rung 2 is the drain's weak rung, so it is the one clause that got a why (2026-08-20).** "Already in this codebase" assumes accumulated familiarity that a fresh worker in an isolated worktree does not have, which is exactly the condition that produces re-implementation. The clause names the qmd/tree prior-art search as the mechanism that makes the rung reachable. Two guards travel with it: the acceptance matrix counts as explicitly requested (so rung 1 cannot trim a criterion, and the never-simplify list stays absolute), and the ladder's terse code-first output convention does not replace `READY_FOR_REVIEW` — including the `ceiling:` marker, which belongs in the code rather than the handoff, per the locus rule that motivated it upstream.
- **The Standards axis got the vocabulary and a severity bound in the same edit (2026-08-20).** A `bc-codebase-design` pointer alone would have opened an unbounded finding class: structural taste is infinite, and a review axis that can reject on shape converts every slice into an architecture debate the issue never funded. So the rule requires the deletion test *before* a finding is raised and grades shape preference Minor unless it breaks stated behavior, leaves it untestable through any interface, or duplicates the repository. This is the same bound as `bc-code-review`'s findings-are-not-obligations guard, applied to a new axis.
- **Documentation is a review axis input, not a review output (2026-08-20).** `bc-codebase-docs` was already written to be loaded by a Standards pass, and `bc-code-review` does load it — but the drain's Standards axis is a separate contract that said only "documentation risks" and never named it, so a drained slice could change behavior and leave its owning README contradicting the code with nothing to catch it. Wired on both sides: the worker updates the owning page in the same diff, the reviewer checks for a stale owner, change-narration, or an invented `docs/` tree. Two bounds keep it from becoming a documentation project inside a rework round — absent documentation is never a finding (a repository that keeps none owes none), and the remedy is the owning hunk rather than a rewrite.
- **Resume was the loop's real durability hole (2026-08-20).** The drain had recovery bundles for *deferred work* and remote claim branches for *ownership*, but no contract for a run that simply died between phases: nothing said which claims a fresh driver owned, which worktrees held unreviewed diffs, or whether to adopt or release them. `bc-delegate-investigation` carries exactly this rule (recover before relaunch) and the drain inherits none of it, because `bc-delegate-investigation` is read-shaped and hands implementation fan-out *to* this loop — so the loop that can lose the most had the least. The remote claim refs became the authoritative index for the stated reason that they are the one record not living in the context that vanished. The sharpest decision: an adopted worktree takes **full fresh review on every axis**, discarding prior approvals, because a standing approval is a durable record and a record nobody can read is not one. The fail-safe mirrors the recovery contract's — an unaccountable claim is reported, never released and never cleaned, since the inconsistency is the evidence.
