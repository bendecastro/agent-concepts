# Concept: bc-setup-project

User-invoked adaptive initializer. Code, ops and hybrid scaffold the visible layout (work items in `work/`, decisions and research in `docs/`, root `glossary.md`, agent mechanics in `.bc-agent/`); learning and knowledge keep the `.bc-agent/` vault. Hybrid adds the paths the hosted `bc-teach` adapter maps. The visible layout has deterministic tests but has not yet been pressure-tested with a consuming agent.

## Design decisions

- **Plain `Spent:` line and no `gh` noise (2026-11-27).** When no session is counted, `work_spent.py` prints `Spent: not measured (no agent session for this item was found)` instead of `0m active, 0 tokens, cost unknown`; `work_index.py --check` accepts it. The recon checks `gh` and GitHub issues only when a remote points at GitHub, and otherwise says nothing about `gh`. Source: the 2026-11-27 stranger rerun (`docs/research/2026-11-27-stranger-end-to-end/README.md`, section Rerun after the fixes).
- **Kernel is a read-only survey check (2026-11-27).** The project scaffold does not own per-harness configuration. Report a missing kernel and its install instructions, staying silent when it is present. A decline records one line in the project’s existing ideas role; it does not alter the scaffold, starter items, teach/wiki integration, or any of the generated paths or work/validation contracts that the other relationship edges cover. See the [pressure results](tests/pressure-kernel-survey-results-2026-11-27.md). Since 2026-11-27 the Pi suggestion is the Agent Concepts Pi package itself (which includes the kernel) or re-enabling its kernel extension in `pi config`, not a separate `./packages/agent-kernel-pi` install; the kernel-survey pressure scenario still names the old command and was not rerun.

- **Carry-on reuses active work without taking it away from a live holder (2026-11-26).** The priority list orders eligible work; it cannot override unfinished active work. The scaffold puts the scan order and the holder check together in the generated work rules. See [carry-on pressure results](tests/pressure-carry-on-results-2026-11-26.md).

- **Generated instructions work without local helpers (2026-11-26).** The validation page and gate header say to run the gate directly if there is no offload wrapper. The offload fallback does not change the gate command.

- **Work data as JSON (2026-11-25).** `work_index.py --json` prints every item in all four folders (header lines, steps with checked state and Notes, Outcome) under a `format_version` that changes only on a breaking change, and writes nothing; [work-data.md](body/work-data.md) lists each field, its source and whether it is stable, best-effort or planned. A separate tolerant reader is used rather than the table's `read_item`, because done and dropped items need not carry `Blocked by:` and must not fail the output. Provenance: work item 025-dashboard-data and decision 0003 (work data lives in work-item lines and git history). Tests: `tests/test_work_index_json.py`.
- **`Needs owner:` line (owner decision 2026-11-26).** The work-item rules and template carry an optional `Needs owner: <what the owner must decide or do, and when>` line for an item that will need an owner decision or action before or during its build, removed once settled; `--json` reports it as `header.needs_owner` (an added field, so `format_version` stays 1). Why: the owner's dashboard shows it so the owner can plan time away. It differs from `Waiting on owner:`, which parks an item on a question already asked. Migration: [MIGRATIONS.md](MIGRATIONS.md#needs-owner-line).
- **`Changes UI:` line (owner decision 2026-11-26).** The work-item rules and template carry an optional `Changes UI: <what the user will see change>` line for an item whose build changes what users see or operate (screens, controls, labels, keys, layout, styling), kept current as the plan changes; `--json` reports it as `header.changes_ui` (an added field, so `format_version` stays 1). Why: the owner's dashboard shows it, so the owner can plan when to review UI work. Migration: [MIGRATIONS.md](MIGRATIONS.md#changes-ui-line).
- **Review and Gate lines (2026-11-25).** A step's Notes carry `Review: <approved | changes requested> by <reviewer> <YYYY-MM-DD>` and `Gate: <pass | fail> <command> at <commit> <YYYY-MM-DD>`, one line per result, oldest first; `--json` gives each step `review` and `gate` lists (fields null on a malformed line, raw `text` kept) and `--check` warns on a malformed one. `<commit>` is the SHA the checked tree was built on, because the landing commit cannot cite its own SHA. The scaffolded work-item rules and the Finish a step row tell agents to write them. Provenance: work item 025-dashboard-data (Stories 5, 7), decision 0003; formats as planned on [work-data.md](body/work-data.md).
- **Spent line (2026-11-25).** `work_spent.py`, installed beside `work_index.py`, prints `Spent: <active time> active, <tokens> tokens, <cost> (estimated; <sources>)` for one item: sessions with an entry in the item's active period (first committed move into `2-active/` to its move out, or now), whose working folder is the project or a current git worktree and whose file mentions the item name. Active time sums gaps between entries capped at 15 minutes; Pi gives cost, Claude Code and Codex tokens only, each tool's count or `no files` is named, other tools are not counted. It imports `work_index.py` for the history (no bytecode written). Roots default to each tool's home folder and are overridden by `WORK_SPENT_*_SESSIONS` so tests read only hand-made fixtures. `--json` on the work index parses the line from the Outcome; `--check` warns on a malformed one. The scaffolded rules and the Finish or drop row tell the agent to paste the line unchanged. Matching on mention and current worktrees is best-effort: a session that names the item in passing is counted, one in a removed worktree is not, unless it is a Pi child (subagent) session of a counted parent (2026-11-25: such children count whatever their folder and mention, inside the period, and `--json` names them `via: child of <parent file>`). Provenance: work item 025-dashboard-data (Story 6), decision 0003. Tests: `tests/test_work_spent.py`.
- **Item history from git (2026-11-25).** Each JSON item gains `history`: `created`, `moved` (lifecycle folder change) and `ticked` (a `- [ ]` step line turned `- [x]` in a commit's diff) events with commit date and SHA, from one `git log --follow --raw -p` call per item (without `--reverse`, which breaks `--follow`). Uncommitted, no repository or no git gives `[]`; best-effort because it depends on git keeping the rename trail. About 1.4 s for this repository's 25 items. Provenance: work item 025-dashboard-data, decision 0003. Tests: `tests/test_work_index_history.py` (scratch git repository; failed before the change).
- **Placement by kind (owner decision 2026-11-24).** An item may carry `Kind:` (what it is; `Source:` says who filed it). `work_index.py --check` places a new item whose kind is on the project's `Top kinds:` line (default security, bug, build, architecture; `none` off) directly below the top group, the run of top-kind items at the head of `work/order.md`, oldest first, and never above its blocker. Placement follows the kind, not the filing skill, and the top-group rule stops a burst of new top items from jumping ahead of top items the owner already placed.
- **Visible layout for code, ops and hybrid (2026-11-12).** Provenance: the "Resolved decisions" of [the visible-layout plan](../../work/3-done/2026-11/018-bc-init-agent-visible-layout.md), agreed with the owner; this is its work package W1. Knowledge is visible and `.bc-agent/` holds agent mechanics only (`AGENTS.md`, `map.md`, `log.md`, `conventions/`, `references/`, `templates/`). Work items move through `work/1-planned/`, `2-active/`, `3-done/<year>-<month>/`, `4-dropped/`; the folder is the status, so the work-item template has `Why:`, `Done when:`, optional `Issue:`, `## Steps`, `## Outcome` and no `Status:`. Ideas are lines in `work/0-ideas.md`; a plan is a work item, so no plan template or plans folder is generated. Decisions and research live in `docs/decisions/` and `docs/research/`; empty folders carry `.gitkeep`, and the four `work/` stage folders keep theirs permanently so every stage stays in git when empty. `docs/PRD.md`, `ARCHITECTURE.md`, `.agents/skills/` and `.agents/agents/` are named in the table and created on first need, not as placeholders. `tasks/`, `project/`, `decisions/`, `research/`, `scratch/`, `out-of-scope/`, `index.md`, `home.md`, Obsidian settings and `conventions/planning-workflow.md` are no longer generated for these archetypes.
- **Generated work index and stages (owner decision 2026-11-16).** Visible layouts get `.bc-agent/scripts/work_index.py` (Python stdlib, ported from project A's `work-index.mjs` script), a `work/README.md` with the generated block's markers, a `Stages:` line (default `now, next, later, unscheduled`) and an "every open item has a `Stage:` line" rule in the generated Work items section, the index run in the Begin/Finish-a-step/Finish-or-drop rows, and `Stage:` directly under `Done when:` in the template. Refresh only the script with `cp "$AGENT_CONCEPTS/concepts/bc-setup-project/body/work_index.py" .bc-agent/scripts/`; `--force` also refreshes it, along with every other `.bc-agent/` file. The canonical copy is `body/work_index.py`, which `bc-work-sync` relies on. The generated text now says "status folders" for `1-planned/`…`4-dropped/`, since "stage" names the `Stage:` value. A fresh `work/README.md` contains the generated empty index and passes `--check`. Edges: `bc-wiki-maintain`'s agent-mechanics check allows `scripts/` (updated in the same change, its tests failed without it); `bc-plan-to-pipeline`, `bc-drain-issues`, `bc-triage` and `bc-improve-codebase-architecture` create or move items through the generated template and work-item rules (each SKILL says so), so they pick up the `Stage:` line and the index run from the project; `bc-handoff`, `bc-diagnosing-bugs`, `bc-domain-modeling`, `bc-prototype` and `bc-teach` only resolve paths and are unaffected. Those skills still say "stage folders" for the status folders; not renamed here. Upgrade: [MIGRATIONS.md](MIGRATIONS.md#work-index).
- **Blocked-by ordering (owner decision 2026-11-22).** The work-item template has `Blocked by:` under `Stage:` (full item names or `nothing`), and the generated Work items section adds four rules: every open item has a `Blocked by:` line; a building block gets its own item; look for overlap in open items and the ideas file before creating one; one item, one deliverable. `work_index.py` rejects a missing line, unknown or dropped blockers, self-blocks and cycles, and orders the table topologically (active, then ready, then most open items transitively unblocked, then the `Stages:` order, then name) with `#`, `Waits on` and `Unblocks` columns; a blocker in `3-done/` is satisfied. Provenance: the owner's adoption of this rule set in one of their projects (project B), whose script and tests were ported here with the generic default stages kept. Edges: `bc-plan-to-pipeline`, `bc-drain-issues`, `bc-triage` and `bc-improve-codebase-architecture` write items from the project's template under its work-item rules, so they pick up the line from the project (as with `Stage:`); `bc-work-sync` runs the script and now reports missing and invalid `Blocked by:` lines (updated in the same change); `bc-wiki-maintain` only allows the `scripts/` folder and is unaffected. Upgrade: [MIGRATIONS.md](MIGRATIONS.md#blocked-by). Since 2026-11-23 the script accepts an open item without a `Stage:` line and sorts it after every stage (an unknown stage is still an error); the generated rule still asks for the line. Why: several projects keep stage-less items, and their local copies already accepted them, so the canonical copy blocked the owner-order rollout.
- **Owner order (owner decision 2026-11-22).** An optional `work/order.md` holds the owner's ranking of open items as a numbered list (`1. 012-search-ranking`; other lines ignored). `work_index.py` ranks active items first, then the planned items an active item is transitively blocked by (spec amendment 2026-11-22, so blockers of active work are not pushed behind a ranked unrelated item), then puts listed items in list order, ahead of unlisted ones and ahead of the ready/unblocked/stage tiebreaks; blockers still win; an unlisted blocker does not inherit its listed item’s rank. Dashboard-written orders list every open item, so this affects only hand-written partial lists. The order applies when every item says `Blocked by: nothing`. Names in `3-done/` or `4-dropped/` (and their month folders) are skipped unless an open item has the name; order-line digits are ASCII only; an unknown or repeated name is an error. The three tiers (active, blockers of active, other planned) apply with or without the file (spec amendment, round 3); without it there is only no owner rank. `Blocked by:` stays required on every open item even when `order.md` exists. The format and key are a spec shared with the owner's dashboard, which reads and writes the same file (unknown/repeated names are warnings there). The generated Work items section gains one rule naming the file. Edges: `bc-work-sync` runs the script, so its `--check` now also reports bad `order.md` names (its SKILL says so, updated in the same change); other writers of items are unaffected. Upgrade: [MIGRATIONS.md](MIGRATIONS.md#owner-order). Since 2026-11-23 (owner request) `--check` also fails while `order.md` leaves out an open item or lists an item above one it waits on, naming where an unlisted item goes (directly above the first listed item that waits on it, else the bottom), and the generated Work items section adds "Never reorder `work/order.md`; place what you add" (check with the owner before a `Blocked by:` line that inverts the order). The table is still built from a partial or inverted file; only `--check` refuses it. Why: the dashboard writes every open item and refuses a blocker below its dependant, so these faults come only from agents, and an agent that added an item and a blocker without listing it sent three of the owner's ranked items to the bottom. `bc-work-sync`'s SKILL names the new faults (same change).
- **Ready and waiting lines (owner grill 2026-11-25).** The work-item template, the `.bc-agent/AGENTS.md` work rules and `work/README.md` document two optional header lines: `Ready for agent: yes` (`bc-pipeline-to-done` may build the item unattended; `bc-plan-to-pipeline` writes it only when every step states done-criteria and out of scope) and `Waiting on owner: <question>` (parked; not ready until the answer is recorded and the ready line restored). `work_index.py` marks both in the Folder column and rejects an item with both, as an error like its other contradictory-header checks. Provenance: [work item 023-pipeline-to-done](../../work/3-done/2026-11/023-pipeline-to-done/requirements.md).
- **Staged validation, one gate command, CI on it (owner decisions 2026-11-19).** Visible layouts get a `conventions/validation.md` with three stages, one owner each: While working (worker, job or reviewer: typecheck, lint, affected unit tests; no browser/e2e tests, no full gate; 60 s budget), Full gate (the integrating session: `<offload-wrapper> --budget 300 -- scripts/gate` in the background with a wake, once per integrated tree, tree SHA and result recorded for reviewers to reuse, one per host, rerun only failing tests for a flake, two over-budget runs in a row open a work item before more features; every browser/e2e test runs here) and Release. `./scripts/gate` runs its steps directly, with no `<offload-wrapper>` inside, so the generated `.github/workflows/gate.yml` runs it unchanged on a clean checkout; the root `AGENTS.md` says to check the latest trunk CI run before landing, red blocks. The stub gate exits non-zero until filled: a vacuous green gate would report success for checks nobody wrote, which is how a trunk stays red or unmeasured unnoticed. Provenance: project A's `validation.md` (stages and full-gate rules) and the agent-time-sinks council memo (2026-11-19: an empty TODO validation page was filled with "full gate before every commit", packets pasted it into workers, and CI was red 30/30 unnoticed). `VALIDATION` for learning and knowledge is unchanged.
- **Ops keeps its operational knowledge.** `docs/components/` with the `component` and `finding` templates; findings go to `docs/research/`, plans are work items.
- **Open questions are work, not a folder (owner decision 2026-11-12).** Ops and hybrid no longer generate `docs/open-questions/` or an open-question template. The generated `.bc-agent/AGENTS.md` of every visible-layout archetype says, with the work-item rules: a question that blocks a piece of work is a step in that work item; a standalone question someone must investigate is a planned work item whose answer lands in `docs/research/`; one not worth an item yet is a line in `work/0-ideas.md`. Why: `work/` stays the single place that shows what is pending.
- **Hybrid = ops layout plus exactly the teach adapter's mapped paths** under `.bc-agent/` (`learning/`, `sources/`, `concepts/` with `entities/` and `syntheses/`, `questions/`, `sessions/`, `references/teach-skill.md`, `references/teach-resources.md`, `templates/learning-session.md`, `index.md` as the teach catalog). Why: `bc-teach` pins those paths, and changing them belongs to the teach redesign.
- **Hybrid has one glossary (owner decision 2026-11-12).** The hybrid adapter maps `bc-teach`'s Glossary to the project's root `glossary.md` (`../glossary.md` from `<teach-root>`), shared with the project: `bc-teach` adds and refines the terms the learner needs in the file's one-line format and does not remove or redefine project terms without asking; `bc-domain-modeling` and planning skills keep using the same file. Hybrid no longer generates `.bc-agent/project/overview.md`, and `.bc-agent/project` counts as earlier layout for hybrid as for code and ops. `is_valid_teach_adapter` accepts exactly two maps, the vault map and the hybrid map, which differ only in the Glossary row; the learning archetype keeps the vault map. Provenance: resolved decisions of [the visible-layout plan](../../work/3-done/2026-11/018-bc-init-agent-visible-layout.md).
- **Learning and knowledge keep the vault, byte-identical to before.** Why: `bc-teach` reads exact vault paths and its tests pin them. `tests/test_visible_layout.py` compares their output with the scaffold at `e27f2e6`.
- **Existing projects are not migrated by the scaffold, and are refused by default.** On a project with earlier-layout paths under `.bc-agent/`, a visible-layout run writes nothing, names the paths and exits non-zero; `--allow-earlier-layout` creates the missing files beside the old ones instead. Why: two sets of homes for the same knowledge would both look current, and plan Q22 moves a project deliberately in one pass. See [MIGRATIONS.md](MIGRATIONS.md#visible-layout).
- **Migration is a separate, dry-run-first mode that does only the mechanical part (W4, 2026-11-12).** `--migrate` prints the plan; `--migrate --apply` moves whole files with `git mv`, creates the missing layout files, replaces `.bc-agent/AGENTS.md`, deletes only placeholders and unmodified generated files, rewrites relative Markdown links, stages and does not commit. Everything needing a reading of content (task lists, plans, overviews, findings, open questions, catalogs, unrecognised files) is printed with the owner's rule and left untouched; the skill body tells the agent how to apply each rule. Why: a move is safe to automate, but deciding which tasks are still open or what an overview's terms are is not, and inventing work-item fields for finished tasks would be fiction. Owner decisions (2026-11-12): only open work becomes items, finished lists stay as one dated research record; `docs/adr/` moves to `docs/decisions/`; issue drafts live inside their parent item; a project without a vault gets a fresh scaffold. A wikilink naming a moved file becomes a relative Markdown link (owner decision 32): the Obsidian settings are retired and plain links resolve in any viewer. A bare name matching several files is left and reported rather than guessed, and wikilinks to files that stay are untouched, since the change is about not breaking links, not converting a vault. Provenance: the plan's owner decisions 27–30 and 32 and a trial on clones of one code and one ops project.
- **`--force` stays inside `.bc-agent/`.** Root `glossary.md`, `work/` and `docs/` hold the project's own content and are never overwritten; root `AGENTS.md` needs `--force-root`.
- **Project agents live in `.agents/agents/` (owner decision 2026-11-12).** The `project-agents` row, previously undecided (`—`, "ask the owner"), names `.agents/agents/`, created on first need, one `local-<name>.md` file per agent beside `.agents/skills/`. Why: one `.agents/` folder for both kinds of project extension, with the same `local-` prefix that separates project entries from shared ones.
- **Generated text redirects skill defaults to the table.** `.bc-agent/AGENTS.md` tells agents to use the table's path when a shared skill names its own default (for example `docs/adr/`), and root `AGENTS.md` keeps `bc-codebase-docs` off the table's record paths. Why: shared skills are written for several layouts, and until the consumer skills read the table (W3) this rule is the only redirect.

- **W3 review fixes (2026-11-12).** A large work item's folder holds `plan.md` (its `## Steps` are the slices) and `requirements.md`, plus any evidence; no separate slice files, because the steps already are the slice map (decision 10 refined in review, pending the owner's confirmation; recorded in the plan). The visible runway page keeps the default `docs/research` and `docs work` in its snippet and tells the agent to substitute the table's research and work paths when the project changed them. The map upgrade note fires only for an inline-code bullet whose target is an existing file inside `.bc-agent/`, so a bullet naming a project file created on first need (for example `docs/PRD.md`) is not flagged. Standalone teach state is matched by exact directory-entry name, so a hybrid project's shared root `glossary.md` is not mistaken for `GLOSSARY.md` on a case-insensitive filesystem. Provenance: the W2/W3 review of [the visible-layout plan](../../work/3-done/2026-11/018-bc-init-agent-visible-layout.md).

- **Validation page names the test levels (2026-11-17).** Visible-layout `conventions/validation.md` lists tdd's three test levels with `Level 3: off` and the `.hypothesis/`-style cache rule (gitignored machine-local state; sync-tool ignore only in a synced folder, conditional since 2026-11-27). Only visible archetypes get it: learning/knowledge vaults keep the base template byte-identical. No migration: existing projects gain the entry when their first property test lands. Covered by `test_validation_page_names_three_test_levels_with_level_3_off`. Later the same day the Level 3 entry became a bare `Level 3: off` followed by commented examples of the owner-only `Level 3: on` and `Level 3 declined` lines, copied from tdd's `formal.md` (covered by `test_validation_page_level_3_is_off_with_owner_only_on_and_declined_formats`).

- **The scaffolded gate names no machine tool (2026-11-19).** `validation.md` tells agents to start the scaffolded gate script through the machine's offload wrapper if its agent instructions name one, with a measured, non-enforced 300 s budget; its header mentions the wrapper but not the budget. scaffold.py has no machine-config seam (only the vault path and archetype), and adding one would be speculative. Why: scaffolded projects and this repository are public; a stranger's machine may have no wrapper.

- **Design README (2026-11-21).** Code, ops and hybrid scaffolds write `docs/design/README.md` (current truth vs the project's decision log, where a rule lives, the before-adding-a-control step, empty Pages and Checks lists; no fixed page list) and a prose line in `.bc-agent/map.md` routing design, UI and CLI wording work to it. Existing projects get the README on their next run (never overwritten); an existing map that lacks the line produces an upgrade note. No new "Where things go" role: the owner decided day one creates only the README and the map line. The method is `bc-ui-design`'s `design-framework.md`. Covered by `tests/test_design_readme.py`.

- **Pickup rule and `Planned:` line (2026-11-24, owner decision).** The generated Work-items rules say a planned item without a `Planned:` line is run through `bc-plan-to-pipeline` (settled source, in place) before it moves to `2-active/`, whether by hand, on "carry on" or by a drain; when no one can answer an open question it goes to the configured destination or into the item’s `Waiting on owner:` header if no destination is usable. The item stays planned and the agent takes the next eligible one. The "Begin agreed work" row points at that rule. The work-item template carries an optional `Planned:` line under `Source:`. `work_index.py --check` warns on stderr about each planned item without the line but keeps its exit code, because existing projects hold dozens of legacy planned items and every producer's `--check` placement step would otherwise fail. The generated `work/README.md` table does not show the marker: a new column would churn every project's index for a transitional signal the warning already gives. ## Interface: the "Where things go" table

Later work packages and other skills read project paths through this contract, not by assuming them.

- **Location and heading.** `.bc-agent/AGENTS.md`, section `## Where things go`.
- **Columns.** A Markdown table with header `| Role | Path | Notes |`. Path is a backticked path relative to the project root, or `—` when the role has no decided path. Notes say, among other things, "created on first need" for a path that may not exist yet.
- **Role keys** (`LAYOUT_ROLES` in [`body/scaffold.py`](body/scaffold.py)): `work-planned`, `work-active`, `work-done`, `work-dropped`, `ideas`, `decisions`, `research`, `glossary`, `requirements`, `architecture`, `project-skills`, `project-agents`. Ops and hybrid add `components`; hybrid adds `teach-workspace`. Optional, never generated (`OPTIONAL_LAYOUT_ROLES`): `agent-extras`, whose Path cell lists comma-separated `.bc-agent/` entries a tool reads by path (for example `` `.bc-agent/autoresearch/` ``); `bc-wiki-maintain`'s lint reports every other entry under `.bc-agent/` that is not agent mechanics. The shared parser returns only the first backticked path of that cell, so a reader of the full list reads the raw cell.
- **Parser.** `parse_where_things_go(text)` in `body/scaffold.py` returns `{role: path}`. A backticked path is unwrapped; a plain path is returned stripped; only `—`, `-` or an empty cell maps to `""` (undecided). The heading must be a whole line (trailing spaces and CRLF tolerated; `### Where things go` does not count). It raises `ValueError` when the heading is missing, when the section has no table rows, or when a role appears twice. `where_things_go_table(archetype)` writes the table from `layout_rows(archetype)`.

## Interface: migrate mode

`scaffold.py --root <repo> --slug <slug> --archetype code|ops|hybrid --migrate [--apply]`. Exit 1 with nothing written on a refusal (not a git repository root, uncommitted changes listed, no `.bc-agent/`, table already present, learning or knowledge archetype, missing `--archetype`, a destination already present as a different file). Output, in order: `Repo:`, `Branch:`, `Archetype:`, then the sections `MOVE` (`old -> new`), `CREATE`, `REPLACE`, `DELETE`, `KEPT (review by hand)`, `NEEDS JUDGMENT` (`path — N lines|N files — rule`), `LINKS`, `OTHER REFERENCES`, each item indented two spaces and `(none)` when empty; then `Totals:` and the apply command. `--apply` adds an `Applied:` line and ends with the reminder to work through the judgment list and commit. Details: [MIGRATIONS.md](MIGRATIONS.md#migrate-mode).
