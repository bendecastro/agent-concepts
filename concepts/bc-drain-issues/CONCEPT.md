# Concept: bc-drain-issues

User-invoked AFK executor for a repo's `ready-for-agent` and `rework-for-agent` GitHub issue queue. A preflight-gated driver claims dependency-ready slices, gives fresh workers isolated worktrees, requires independent Spec + Standards approval, permits bounded same-worktree rework, and mechanically lands approved diffs. It closes a parent PRD only after all children complete. Runs after `bc-plan-to-issues`; `bc-` is the user's personal namespace.

## Design decisions

- **Fresh workers, durable packets, isolated worktrees.** The issue/Agent Brief, acceptance matrix, repository context, diff, findings, and validation artifacts—not a parent transcript—form the handoff. A remote no-force `bc-drain-claims/issue-<n>` branch is the cross-run ownership lock; labels are advisory. Worktrees outside the main checkout provide filesystem isolation.
- **Preflight preserves publish and queue safety.** Branch/remote cleanliness, `publish-check.py`, claim authorization, label availability (including `rework-for-agent`), GitHub/PRD access, worktree/recovery roots, qmd mode, and caps are checked before AFK launch. The drain never self-authorizes. Dependencies from bodies/comments must be closed and unclaimed before dispatch.
- **Risk controls are proportional.** Ordinary slices use explicitly low effort. Compatibility replacement/retirement, migration/cutover, systemd/external-service semantics, and broad public surfaces use medium effort plus a bounded read-only contract audit. Replacement audits inventory the entire old public interface from source/tests/help and map requirements to evidence. Material external-platform claims are checked against available primary docs/help rather than trusted from repository prose; narrow new-command and string-presence tests previously missed costly compatibility defects.
- **The contract audit inventories guards, not only interfaces (2026-07-27).** Added a `guard/rejection clause -> can-its-inputs-differ-in-production evidence` row after a real drain of an inert-guard issue reproduced the very defect it was fixing: the worker deleted the named tautological clause and left a sibling clause tautological, then made it *harder* to see by substituting an expression with an identical runtime value. Independent Spec review caught it, but the audit is the cheaper place — it runs before implementation. The row is mandatory for every guard a guard-issue's diff touches, keeps, or relocates, because fixing one member of the class while leaving another is the observed failure. Recorded in `review-contract.md` too, since a driver-materialized packet is the only instruction an AFK reviewer sees.
- **Cached baseline, targeted editing checks, final full validation.** Full project validation runs once per base SHA for a baseline and once before landing. Editing/rework/review use targeted evidence and baseline deltas. This retains regression detection while avoiding repeated full-suite cost.
- **Deterministic gate before lean independent review.** The driver mechanically checks acceptance coverage, status/diff scope, targeted validation/baseline delta, no staged/unrelated files, and external evidence before spending model review. Fresh read-only agents get minimal packets and strict compact JSON; the packet is authoritative, so generic absent `plan.md`/`progress.md` conventions cannot block them. They never run the full suite.
- **The driver materializes the review packet; reviewers never re-derive it (2026-07-26).** Diff, changed-file list, matrix, and validation are written once per round outside every worktree, and reviewers read those paths instead of re-running `git status`/`git diff`. Independence is a property of reasoning, not of repeating the driver's deterministic Git work. The packet's `diff_sha256` and acceptance-matrix→file map also supply the identity and mapping that standing approvals and invalidation triggers need, so one artifact serves economy, determinism, and auditability.
- **Standing approvals with deterministic invalidation supersede re-reviewing every axis every round (2026-07-26).** An approval binds to the exact diff hash it examined. After a rework round the raising axis always re-reviews; an approving axis re-reviews only when a driver-computed trigger fires on the delta, and an unmappable delta invalidates both. Before landing, every axis must hold a standing approval matching the final diff hash, so "both axes approved the landed diff" stays literally true while the same question is not paid for twice. This generalizes the pre-existing rule that a rebase changing the reviewed diff invalidates approval.
- **Review tiers make axis count proportional to risk (2026-07-26).** High-risk slices and any diff touching a public interface, security/privilege boundary, or installed/launcher topology keep two independent axes. Ordinary slices get one combined reviewer that works both scopes. This is the only economy control that genuinely trades independence, so it is bounded by one-way escalation: a pre-review gate rejection or any Critical finding moves the issue to tier 2 permanently, and tier plus reason are reported per issue for human audit.
- **Rework re-evidences a narrowed scope with carry-forward (2026-07-26).** v2 stopped the reworker rebuilding from scratch but still made it repeat the full review-ready gate each round: re-map every acceptance row, re-run targeted validation broadly, re-inspect the whole diff. The reworker is the priciest unit after the initial build (Gate B: 50,425) and is paid up to three times, so that repetition dominated contested issues. It now re-evidences only the rows implicated by the findings, the rows whose mapped files its fix touched, and anything already failing or flaky; other evidence carries forward. Full-scope status/staged/unrelated inspection is dropped entirely because the driver's deterministic gate re-checks it immediately afterward. This mirrors standing approval on the review side—carried-forward evidence with deterministic, driver-verified invalidation—so one matrix→file map serves both. **Accepted trade-off:** a fix breaking an untouched, unimplicated row is now caught by the driver's final full validation rather than mid-round, which wastes that round's review tokens but cannot land a regression, because final full validation still gates the commit. The touched-row rule and the always-rerun failing/flaky set cover the common cases.
- **Reproduction is gated on a formed finding (2026-07-26).** "Bounded targeted reproduction" read as licence for exploratory command runs. A reviewer may now run commands only after naming a candidate Critical/Important finding, at most two per finding, purely to prove or refute it. Refuted hypotheses are dropped silently.
- **Deployment Gate B uses a deterministic trace; natural contest remains ecological pressure (2026-07-27).** Autonomous model discovery could not reliably produce the two Standards-only reworks needed to measure selective re-review: the preserved natural v2 attempt stopped after one. The deployment benchmark therefore locks S0 → S1 → S2 and v2/v3 dispatch topology while keeping reviewer JSON, reworker patches, Pi lifecycle usage, and correctness real and independently verified. Golden transitions preserve comparable topology; model mismatch fails fidelity rather than changing rounds. Because Spec skips the two intermediate v3 rounds, its S0 hash cannot land and one focused S2 Spec hash-sync is mandatory.
- **Bounded same-worktree rework supersedes one remediation (2026-07-25).** Initial review may be followed by up to three fresh compact rework/re-review cycles. Continue only on material progress; the same unresolved finding after two attempted fixes defers. Minor findings do not block. Issue #29 showed the former second-finding terminal policy discarded useful fixable work rather than increasing safety.
- **Fresh reworker narrowly supersedes the rejected separate-fixer decision (2026-07-25).** A reworker does not reconstruct the issue from scratch: it receives the existing worktree, acceptance matrix, unresolved findings, and validation evidence. This keeps TDD artifacts and breaks self-review bias without replaying an ever-growing implementation context.
- **Fixable is not human-blocked.** `HUMAN_BLOCKED` is only for decisions, access/resources, ambiguous contracts, or irreparable environment failures. Budget/round exhaustion becomes `REWORK_DEFERRED` with `rework-for-agent`, a validated machine-local recovery bundle, and a portable Agent Rework Brief. Repeated infrastructure failure is `SYSTEMIC_FAILURE`.
- **`HUMAN_BLOCKED` comments are for the human who will unblock (2026-08-18).** Decision or missing access first, options and consequences, then exact evidence. SHAs/paths/commands stay literal. A thin utterance clause, not a `plain-language` load — workers still return `BLOCKED_NEEDS_HUMAN` with evidence; only the driver's GitHub comment is human-facing. The final stop-and-report and Agent Rework Brief stay mixed/agent-facing and were deliberately left alone.
- **Recovery is exact and fail-safe.** A versioned bundle records a binary-safe tracked patch, safe untracked regular files, acceptance matrix, findings, validation evidence, identities, hashes, and exclusions. Exact matching-base identity uses a canonical temporary-index Git tree OID rather than tar metadata or an improvised diff hash. Ignored/cache/secret/unsafe/out-of-scope content is forbidden. Changed-base restore requires three-way application, entire-diff inspection, validation, and full re-review. Failure preserves evidence and routes safely rather than guessing.
- **Provisional phase-boundary budgets.** Soft 200k and hard 300k child-token caps are checked only after a child returns; active mutation workers are never interrupted mid-write. Soft crossing narrows investigation; hard crossing captures/defer before another child. Round caps are the harness-agnostic fallback. Two consecutive token deferrals stop new launches. These defaults remain provisional pending three comparable real drains.
- **Driver owns landing.** Workers own code/tests/validation and never commit, push, close, label, claim, or clean. After both reviews approve, the driver inspects the reviewed diff, performs the final full validation, commits only issue work, rechecks publication, pushes `HEAD:master`, closes with evidence, and releases resources. A rebase that changes the reviewed diff invalidates approval and requires validation plus focused fresh dual review.
- **PRD closeout and recurring-defect tune remain global.** Only the driver can see all children and close a completed parent. Failure shapes recurring at least twice may additively patch later run-local packets, never canon or gates; patches/triggers are reported for later user promotion.
- **TDD/diagnosis/autoresearch composition remains.** Feature work uses thin RED/GREEN/refactor increments; bug/performance work diagnoses from a red-capable reproduction; metric refinement occurs only after GREEN with correctness and objective improvement gates. Workers search a driver-refreshed qmd collection but never index it.
- **Agent-agnostic canon with concrete Pi economy.** State, packets, contracts, round caps, and recovery semantics work in any harness. Pi installs minimal `bc-drain-auditor`, `bc-drain-worker`, and `bc-drain-reviewer` roles with no unrelated inherited project context/skills or generic plan/progress reads, plus compact subagent tool descriptions. Other harnesses use equivalent fresh packets. Harness sessions/artifacts stay outside issue worktrees so metadata cannot fail scope gates or enter recovery bundles.

## Measured basis

Gate B measured review at 61,012 of 277,012 child tokens (22%) on a *clean* v2 issue: Spec 24,104, Standards 36,908, one round, no re-review. The exposure is the multiplier rather than the single pass—an initial review plus three permitted rework cycles dispatches up to eight reviewer children, roughly 244k tokens at those rates, most of it re-reading a diff an axis already approved. v3 therefore attacks repetition (standing approvals, selective re-review), duplicated derivation (driver-materialized packet), disproportionate axis count (tiers), and ungated exploration (reproduction budget). Because clean and probabilistic single-rework fixtures cannot exercise selective re-review reliably, v3's deployment Gate B uses the deterministic two-rework trace; the natural contested fixture remains complementary ecological evidence.

Issue #29 recorded 16 child implementation/review runs totaling about 1.89M child tokens and $28.76 (parent excluded). Two failed drains spent about 621k tokens and discarded useful diffs; the later normal implementation spent about 1.27M more before landing. Review found real compatibility and systemd defects, so v2 preserves dual review while removing lost-work, broad-context, repeated-full-validation, and false-human-blocker costs. This evidence explicitly supersedes the old one-remediation limit and the broad rejection of a separate fixer.
- **Acceptance evidence must discriminate, not merely exist (2026-08-20).** The driver's deterministic gate proves every matrix row *has* evidence and that rework re-evidenced every touched row. Neither asks whether the evidence would look different had the criterion been false, so a row can carry a green test that passes for an unrelated reason and clear the gate. The rule went to the Spec reviewer rather than the driver gate deliberately: it is a judgment call, and putting it in the deterministic gate would break the one property that gate has. It is scoped to rows implicated by the reviewed diff so it cannot become a per-round full-matrix audit undoing the v3 review economy, and its remedy is discriminating evidence rather than more evidence so it cannot feed a remediation spiral. Deliberately phrased as a sibling of the unfireable-guard rule (*earns credit only once you know…*) so the two read as one family. Origin: the acceptance-mutation idea ingested from unclebob's Acceptance Pipeline Specification, whose own concept was removed as unusable here; this is the part of it that applies to a pipeline whose specs are prose checkboxes.

## Tests

`tests/pressure-drain.md` defines the deployment contract; `tests/run-pressure.py` is the reproducible Gate A runner and `tests/results/` preserves gate records. **v3 Gate A passes 22/22** (reverified 2026-07-27), with check 19 now proving two existing-helper Standards-only reworks skip intermediate Spec, stale Spec hashes cannot land, and a focused final Spec sync binds both axes to the final hash. Checks 18–22 also cover the materialized packet, every invalidation trigger, review tiers/escalation, gated reproduction, and narrowed rework carry-forward. The runner proves deterministic rules, not model behavior. `tests/fixtures/contested-gate-b-trace/` now provides the deployment Gate B harness: independently regenerated canonical identity, locked v2/v3 child slots, real Pi lifecycle usage, outcome-backed reviewer/reworker fidelity, known-failure preservation, and exact-hash landing verification. Its self-test passes; the real same-model/medium A/B has not run, so v3 is still not token-validated. The preserved natural fixture is ecological pressure only; its 2026-07-27 v2 attempt stopped after one rework and remains an invalid non-comparison (205,781 partial child tokens) in `tests/results/2026-07-27-gate-b-contested.md`.

The 2026-07-27 guard-row addition has **no Gate A check yet**: `run-pressure.py` asserts the driver's deterministic rules, and "the audit inventoried every guard the diff touches" is a model-behaviour property, so it belongs in a Gate-B-style run or a dedicated fixture rather than the deterministic runner. The rule is live (symlinked body) and untested; its field basis is one observed drain where a reviewer caught the defect but the audit did not look for it.

v2 Gate A passed 17/17 in a disposable no-network Git/stub/recovery sandbox. Final same-model/medium Gate B compared identical fixture base: v1b 315,474 child tokens versus v2d 277,012 (12.2% fewer); both reviews approved and the final full suite retained only the known baseline failure. The candidate passed the ≤500k gate and stayed below the provisional 300k boundary. Cost rose in the fixture, so the measured win is tokens, not cost. Historical v1 runs remain provenance only.
