# Triage for the bc loop

Turn messy issues, PRs, and bug reports into one of: needs more info, ready for a human, ready for `/bc-drain-issues`, or rejected with durable rationale. This is the intake gate before the plan→issues→drain loop.

Every tracker comment you post during triage starts with:

```md
> *This was generated by AI during triage.*
```

## Where project files go

This skill names project files by role: the **glossary**, the **decisions** folder, the **work-dropped** folder and the **ideas** file. Resolve each role in the "Where things go" table in the project's `.bc-agent/AGENTS.md`. Why: each project has one table, so a project that keeps something elsewhere changes one place and every skill follows. When the project has no such table, use these paths instead:

- glossary: the Glossary section of `.bc-agent/project/overview.md` when it exists, otherwise `glossary.md`;
- decisions: `.bc-agent/decisions/` when it exists, otherwise `docs/adr/`;
- work-dropped: `.bc-agent/out-of-scope/`, one file per rejected concept;
- ideas: none; report the observation to the maintainer instead.

When the table exists, the work-item rules in the same `.bc-agent/AGENTS.md` govern how an item is named, numbered and moved. A project with the table has no `.bc-agent/out-of-scope/`; writing there would recreate a folder the project retired, so a rejection goes to work-dropped.

In a hybrid project the glossary is shared with `teach`: follow the shared-glossary rule in `domain-modeling` (ask before removing or redefining a term you did not add this session).

## States

Use the repo's configured label names if `.bc-agent/conventions/planning-workflow.md` or `docs/agents/triage-labels.md` maps them. When neither file exists (a visible-layout project generates no `planning-workflow.md`), use these canonical labels:

- `needs-triage` — maintainer needs to evaluate.
- `needs-info` — waiting on reporter.
- `ready-for-agent` — fully specified; an AFK agent can run from the issue + agent brief.
- `ready-for-human` — requires human judgment/access/manual work.
- `wontfix` — rejected or already implemented.

Category labels: `bug` or `enhancement` when available. A triaged item should have exactly one state label; if state labels conflict, flag it before changing anything.

## Show what needs attention

When invoked without a specific issue, query the issue tracker and show oldest-first buckets:

1. Unlabeled.
2. `needs-triage`.
3. `needs-info` with reporter activity since the last triage note.

Include external PRs only if the repo says PRs are a request surface. Let the user pick; don't batch-edit a queue unless asked.

## Triage one issue or PR

1. **Gather context.** Read the full issue/PR body, comments, labels, author, dates, and PR diff if applicable. Read the glossary, relevant records in the decisions folder, and prior triage notes.
2. **Check redundancy and prior rejection.** Search the codebase by domain concept for an existing implementation. Read the items in the work-dropped folder if present; surface any similar rejected request or dropped work. If qmd is installed and a global collection covers this repo's project knowledge (`qmd collection list`), `qmd query` the issue's domain terms too — it surfaces prior ADRs and rejections that exact-name greps miss.
3. **Verify the claim.** For a bug, reproduce or fail honestly. For a PR, check whether the diff does what it claims and run the relevant validation if bounded. A confirmed claim makes a stronger agent brief.
4. **Recommend.** Tell the maintainer: category, state, what you verified, and why. Wait for direction unless the user explicitly asked for autonomous triage.
5. **Grill if needed.** If the issue is close but underspecified, run `grilling` + `domain-modeling` to resolve missing decisions one question at a time. If it is broad enough to need a PRD/slices, send it to `/bc-plan-to-issues` instead of pretending one issue is enough.
6. **Apply outcome.**
   - `ready-for-agent`: post an Agent Brief using [AGENT-BRIEF.md](AGENT-BRIEF.md); make acceptance criteria concrete enough for `/bc-drain-issues`.
   - `ready-for-human`: post the same structure, plus why it cannot be delegated.
   - `needs-info`: post triage notes with established facts and specific questions.
   - `wontfix` already implemented: close with a pointer to the existing behavior; do **not** record it in work-dropped. Why: that folder holds decisions not to build something, and an implemented feature recorded there would later read as a rejection.
   - `wontfix` rejected enhancement: record it in the work-dropped folder with the reason, using [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md), then comment and close; in a worktree, do not close the issue until the item exists. The reason is the point of the record: without it the next request for the same thing gets argued again from nothing.

## Quick override

If the maintainer says "move #42 to ready-for-agent", trust them about state, but still offer to write an Agent Brief if none exists. Do not send a bare, vague issue to `/bc-drain-issues` without an explicit maintainer override.

## Handoff rules for `/bc-drain-issues`

A `ready-for-agent` issue is drainable only when the latest Agent Brief has:

- Current behavior / desired behavior, or a clear equivalent for new work.
- Key interfaces or domain concepts without stale file/line instructions.
- Concrete acceptance criteria.
- Explicit out-of-scope boundaries.
- Blockers stated as `Blocked by #NN` when applicable.

For glossary discovery in legacy projects, follow `domain-modeling`’s legacy glossary rule.
