# Plan to Pipeline

Take an idea all the way to agent-ready work **in one pass**, so you never have to remember the order of the planning skills. This is the interactive planning front of the loop. Work lands in the project's work pipeline (a work item), in an issue tracker, or both; the autonomous executor `/bc-pipeline-to-done` builds tracker issues labelled `ready-for-agent` and work items marked `Ready for agent: yes`.

## Choose the mode first

Decide both modes before step 1 and state them in one line (for example "Mode: work item only, from a settled source"), then go straight on to step 1 in the same reply: the mode line is a report, not a stopping point.

- **Tracker or no tracker.** Use the tracker when the project already plans in it (it has `ready-for-agent` issues, or its work items carry `Issue:` lines) or the user plainly asks for issues. A GitHub remote alone is not enough: many projects keep their plans only in work items, and issues created there are a second copy nobody drains. A conditional request ("file issues too if that's how it works", "if the project uses them") is not a plain ask: it defers to the project's practice, so check that practice. The mode line names the evidence for the tracker choice (for example "no tracker: no `Issue:` lines or `ready-for-agent` issues"). **No tracker** otherwise, or when the user asks for work items only: skip every issue step (the parent issue, slice issues, `ready-for-agent` labels, `Issue:` lines, `#NN` references and `pending #NN` tags) and file the plan as a work item only (see [Where project files go](#where-project-files-go)). Without a tracker and without a "Where things go" table, use the fallback change folder and its `tasks.md` as the slice list.
- **Raw idea or settled source.** A **settled source** is a design the owner already settled: an architecture review whose candidates the owner picked, an approved spec, a finished grilling, or an **existing work item** in work-planned (with any settled answers its producer passes along). Do not re-run the full grill on it. In step 1 ask only the questions the source leaves open, in one batch, then continue; with none open, ask nothing except step 2's dependency question. A source that names its test (a bug item's failing reproduction, a review's chosen seam) settles the test seam: write it into the requirements and skip `bc-prd-drafting`'s seam check. A **raw idea** gets the full grill.
- **A map.** When the source is a map (a work item with `Kind: map`, an issue labelled `map`, or a `docs/changes/<slug>/map.md`), work it: read [map-mode.md](map-mode.md) § Work the map and follow it instead of the pipeline below.
- **Existing work item.** Plan it in place: fill its requirements and `## Steps` in its own file (a large item's `plan.md` and `requirements.md`, turning the file into a folder only when it needs more than one slice), and keep its number, name, `Source:` and `Kind:` lines. Never create a second item for it. Why: other items, `work/order.md` and the owner's dashboard already name it.
- **No one to answer.** The owner is absent when they said they are away or not answering, or the run is a drain; an absent owner who adds an instruction ("just pick X") is still absent. Then, when step 1 leaves a question open, do not guess, do not ask in chat and do not wait: in the same reply, file the questions where the owner sees questions (check the project's or machine's instructions). If no place is named or the named place cannot be used, park the existing item: write `Waiting on owner: <question>` in its header (in `plan.md` for a folder item), replacing any `Ready for agent:` line, and name the item in the run report. If there is no item yet, record the questions in the run report instead. Leave the item in work-planned without a `Planned:` line, and continue with the run's next item. Filing the question does not end the run; the run ends only when every item it was asked to carry is started or has a filed question. Why: a guessed answer becomes a decision nobody made, and a run that waits on an absent owner stalls every item behind it.

Slicing (step 7) never stops for approval, in any mode.

This orchestrator composes **model-invoked disciplines only** (`bc-grilling`, `bc-domain-modeling`, `naming-things`, `bc-prd-drafting`, `bc-plan-slicing`) — never another user-invoked orchestrator. It owns the publication steps itself. User-invoked exploration tools (`bc-prototype`, `bc-improve-codebase-architecture`, `bc-triage`) can feed this command, but this command does not invoke them as nested orchestrators. A skill that files planned items (`bc-improve-codebase-architecture`, `bc-find-bugs`) runs this command on them after its own filing has finished: a handoff in sequence, not a nested call, so each run keeps its own gates.

## Where project files go

This skill names project files by role: the **glossary**, the **decisions** folder, the **work-planned** folder, the **ideas** file, the **research** folder and **requirements** (the product-level spec). Resolve each role from the "Where things go" table in the project's `.bc-agent/AGENTS.md`; that file says how.

When the project has no such table, use the paths this skill used before:

- If `.bc-agent/conventions/planning-workflow.md` exists, it is the project's mapping (an older `.bc-agent/` vault): glossary in the Glossary section of `.bc-agent/project/overview.md`, ADRs in `.bc-agent/decisions/`, plans and PRDs in `.bc-agent/project/`. Follow it.
- Otherwise: glossary `glossary.md`, ADRs `docs/adr/`, the change folder `docs/changes/<change-slug>/` with `prd.md` and `tasks.md`, and living specs `docs/specs/<area>.md`.

**The plan is a work item** when the table exists. The fallback change folder is used only without a table; creating `docs/changes/`, `docs/specs/` or `docs/adr/` in a project with a table would scatter the plan outside the folders that show its status.

Write a `Source: <name>` line under the item's header lines, naming what produced the plan: the upstream skill (for example `bc-improve-codebase-architecture`) for a settled source, or `bc-plan-to-pipeline` for a raw idea. In a large plan it goes in `plan.md`. Next to it, write a `Kind:` line (security, bug, build, architecture, performance, tests, feature, docs, ...) when one fits; keep an upstream item's `Kind:` line. When the item will need an owner decision or action before or during its build (a choice only the owner can make, an approval, an account or store action, a hands-on check), write `Needs owner: <what the owner must decide or do, and when>`; remove it once that is settled, recording the decision as usual. Why: the owner's dashboard shows it, so the owner can plan time away. When the build changes what users see or operate (screens, controls, labels, keys, layout, styling), write `Changes UI: <what the user will see change>`, and keep it current when the plan changes; leave it off otherwise. Why: the dashboard shows it, so the owner can plan when to review UI work. When step 8 has written the item's `## Steps`, add `Planned: bc-plan-to-pipeline <YYYY-MM-DD>` below `Source:`; `Source:` keeps naming the producer. Why: the project's pickup rule plans any item without this line before it starts, and `work_index.py --check` warns about it. Place a new item in `work/order.md` where `python3 .bc-agent/scripts/work_index.py --check` says (a top kind goes near the top).

Call the feature's requirements document by the project's term: the requirements role in the table (a work item's `requirements.md` or `## Requirements` section), not "PRD", when the project names it differently. This skill says "PRD" only for brevity.

- **Small plan** (exactly one slice, with or without a tracker): one file `NNN-slug.md` in work-planned, from `.bc-agent/templates/work-item.md`. Put the feature's requirements in a `## Requirements` section above `## Steps`.
- **Large plan** (more than one slice, with or without a tracker): a folder `NNN-slug/` in work-planned holding two files, plus any evidence worth keeping:
  - `plan.md` — the work-item template; its `Issue:` line holds the parent issue (none without a tracker), and its `## Steps` list the slices in dependency order, one checkbox each with title, issue `#NN` (with a tracker), blocked-by and user stories covered;
  - `requirements.md` — the PRD.
  Why two files: the steps already are the slice map, so a separate slices file would be a second copy that drifts.

Number items only from the main checkout: the next number is the highest across all stage folders plus one. In a git worktree, stop after step 3, add one line for the plan to the ideas file, and resume from step 4 in the main checkout; tell the user so. Why: two worktrees cannot see each other's numbers and would pick the same one. Never write a `Status:` line; the item stays in work-planned, and the agent that starts the work moves it.

In a hybrid project the glossary is shared with `bc-teach`: follow the shared-glossary rule in `bc-domain-modeling` (ask before removing or redefining a term you did not add this session).

## Pipeline

1. **Grill.** From a settled source, read it, answer what the source and the code already settle, and ask the owner only the questions left open, in one batch; when none remain, go on to step 2, which still runs. From a raw idea, run `/bc-grilling`: interview one question at a time, recommended-answer-first, breadth-first across every branch of the decision tree before going deep on one. Answer from the codebase anything you can answer yourself rather than asking. If the grill exposes a question that cannot be resolved by conversation or code reading (state model feel, UI direction, architectural runway), pause and recommend the matching pre-planning tool: `/bc-prototype` for throwaway evidence, `/bc-improve-codebase-architecture` for deep-module runway, or `/bc-triage` if the input is an existing issue backlog item that needs a drain-ready Agent Brief.

   **Map or plan.** After the grill, check one thing: is any question still open that this session cannot settle? That is one that needs research this session cannot finish, a prototype to react to, or a task done first (access, a sign-up, data), or one the owner answered with "not sure yet" or "let me think". If any is open, chart a map instead of a plan: read [map-mode.md](map-mode.md) § Chart the map and follow it; steps 2 and 4–9 then run only in the map's Slice step. If none is open, continue with step 2. Size does not decide this; the open question does. The owner can override either way ("make a map", "just slice it"). Why: a plan drafted around an unsettled question bakes a guess into build steps, and a decision made between sessions has no home without a map.

2. **Dependencies — every plan, even when nothing else is open.** Ask now; write a `Dependencies:` line in the item's header lines, always, once the item exists (step 4): in a worktree, carry the answer in the ideas line; without a "Where things go" table, in `prd.md`. Check whether the work will need a library, tool or package the project does not already declare, including test-only ones a discipline calls for: read the project's test rules (its validation conventions and the test levels of the discipline they name, such as `bc-tdd`) and decide which levels this change requires; a required level whose library is not declared (for example a property-testing library for rule-bearing logic) is a new dependency. With nothing new needed, write `Dependencies: none new`, unmarked. For each new one, ask the owner once, in the same batch as any other open question (on its own when none is open): “This needs `<name>` (<why>). May the builder add it, or should it manage without it (<the alternative>)?” A request not to be asked things is not an answer to this question. Record the answer as a line the builder can follow, marked as the owner's answer with its date: `Dependencies: may add hypothesis (test only) (owner's answer, 2026-11-27)` or `Dependencies: none new; use example-based tests instead of property tests (owner's answer, 2026-11-27)`. Mark a line only with the owner's answer, never your guess: `bc-tdd` lets a builder skip a test level or the property library only on the owner's words. The question counts as open for the absent-owner rule above. Why: the builder adds only the dependencies the item names and otherwise stops to ask, so an unasked question costs a stalled build; in a stranger's test run a builder added Hypothesis unasked, and in another, planning skipped the question and the builder parked.

   **A go-ahead approves the plan, not a build.** An approval given while planning ("go ahead", "go ahead with the plan", "yes", "do it") means: finish the plan. Go on to step 3 and end at step 9, writing `Ready for agent: yes` in step 8 when its bar is met: that line lets `/bc-pipeline-to-done` build the item later, and is not a build. This run never edits code or tests and never files its item in work-done, whatever the go-ahead's wording. Why: building is `/bc-pipeline-to-done`'s job, with its own checks and reviews; in a stranger's test run, planning took "Go ahead with the plan." as leave to build, wrote the code, filed the item as done, and the pipeline then found nothing to build. The pull to just do the work is the sign you have reached the edge of the plan (or the map): finish it and hand off.

3. **Capture inline — don't batch.** As terms and decisions crystallize *during* the grill, run `/bc-domain-modeling`: canonical names → the glossary (a pure glossary, no implementation detail); a decision that is costly to reverse AND would surprise a future reader AND reflects a real trade-off → a record in the decisions folder. Capture the moment it crystallizes, not at the end.
   - **Guard:** if the current directory isn't a project where a glossary and decision records belong (empty/scratch dir, unrelated files), confirm with the user before creating docs, or grill without persisting.
   Apply `naming-things` when choosing domain or public code names during the grill.

4. **Open the plan's home and draft the PRD.** With a table, create the work item, or use the existing one you were given (see [Where project files go](#where-project-files-go)); without one, create the change folder `docs/changes/<change-slug>/` (dash-case, named for the feature). Either is the single physical home for this change's planning artifacts; without it they scatter across tracker bodies, comments, and temp files. Run `/bc-prd-drafting`: synthesize from the grill + codebase (no re-interview), sketch and confirm the test seams, and write the PRD to the standard template as the item's requirements (`## Requirements` in a small item, `requirements.md` in a large one) or as `docs/changes/<change-slug>/prd.md`. If pre-planning evidence exists that's worth keeping (a `/bc-prototype` verdict, an architecture-review excerpt), file it in the large item's folder or the change folder, or as a dated folder in the research role for a small item — these otherwise die as temp files. (Step 3's guard applies here as well: confirm before creating docs in a directory that isn't a real project.)

5. **Publish the PRD parent issue (tracker mode only; skip without a tracker).** The parent is a planning/coordination artifact, not a drainable implementation task, so do **not** label it `ready-for-agent`. Its body is a coordination pointer, not a second copy of the PRD (a duplicated PRD drifts from the canonical one): the problem/solution summary plus `Planning artifacts: <path of the work item or change folder>`.
   ```
   gh issue create --title "PRD: <feature name>" --body-file <summary-with-pointer>
   ```
   Keep the returned issue number as the parent and record it on the work item's `Issue:` line (in `plan.md` for a large item). Only implementation slices get the `ready-for-agent` label. A small item with a single slice skips the parent: its one slice issue goes on the `Issue:` line in step 8.

6. **Fold requirements into the living specs.** With a table, do this only when the project has a product-level spec (the requirements role's file exists, or the user confirms the project needs one); merge into the requirements role's file; otherwise skip this step, because the feature's requirements already live in its work item. Without a table, update `docs/specs/<area>.md` (create the file/dir if missing; dash-case area names, one file per capability). This is the durable, normative record of *what the system is required to do* — PRDs and issues go stale by design once their work drains, so the specs are what future grills and agents read instead of re-deriving requirements from code. Merge the PRD's resolved requirements into the relevant spec file(s):
   - Write requirements as current truth ("The system SHALL …") with their key scenarios; rewrite superseded requirements rather than appending contradictions.
   - Tag each new or changed requirement `(pending #<parent>)` (the single slice's issue for a small item; `(pending <work-item path>)` without a tracker) so unimplemented spec text is detectable; whoever touches the spec after the queue drains drops the tag.
   - Stay at requirements level: design rationale belongs in decision records, implementation approach in the PRD, vocabulary in the glossary.
   - **Guard:** same as step 3 — if this isn't a project where such docs belong, confirm before creating them.

7. **Slice.** Run `/bc-plan-slicing`: break the PRD into vertical tracer-bullet slices (prefactor first), check granularity and dependencies yourself, and continue to step 8 without waiting for approval. Show the final slices in your reply as a report, not a question. Only when the user asked in this request to review the slices first, present them as a draft and wait.

8. **Publish the slices.** Without a tracker, publish nothing: write the final breakdown into the item's `## Steps` (a large item's `plan.md`), each unchecked step with slice title, blocked-by references (by step title), user stories covered, its done-criteria (`Done when ...`) and what is out of scope (`Out of scope: ...`), or into `tasks.md` in the fallback change folder; then go to step 9. The step is the work item's Agent Brief: `/bc-pipeline-to-done` builds it without the planning conversation. When every step meets that bar and the item has its `Dependencies:` line (step 2), write `Ready for agent: yes` in the item's header lines, below `Planned:`; otherwise omit the line and say in the report which steps lack done-criteria or out of scope, or that the `Dependencies:` line is missing. Never write it next to a `Waiting on owner:` line. Why: the ready line is the owner's consent to unattended building, and a step without its limits gets built past them. With a tracker: in dependency order (blockers first) so real `#NN` fill each "Blocked by", each with `--label ready-for-agent` and `## Parent #<parent>`. These are the only newly-created issues that enter the drain queue. Each slice body must include an `## Agent Brief`-equivalent contract (desired behavior, key interfaces/domain concepts, acceptance criteria, out-of-scope, blockers) so `/bc-pipeline-to-done` can run AFK without prior conversation:
   ```
   gh issue create --title "<slice title>" --label ready-for-agent --body-file <path>
   ```
   Then record the real numbers. With a table: write the final breakdown into the item's `## Steps` (a large item's `plan.md`), each unchecked step with slice title, its issue `#NN`, blocked-by references and user stories covered; a small item's single slice goes on its `Issue:` line. The folder the item sits in and its checked steps are its status, so add no status text. Without a table: write `docs/changes/<change-slug>/tasks.md` with the same entries. It's the map of the change, written once the real numbers exist — **not** a status board: completion state lives only in the tracker (duplicated state drifts; whoever wants status runs `gh issue list`).

9. **Close out.** Restate the resolved scope; point at the work item or change folder, the glossary, decision records and spec files written, and, with a tracker, the parent issue and the slice issue numbers. Then recommend the handoff: with a tracker, **"Run `/bc-pipeline-to-done` to execute this queue autonomously."**; without one, name the work item as the next work to start, and when it carries `Ready for agent: yes`, say that `/bc-pipeline-to-done` can build it unattended. The run ends here, even after a go-ahead (step 2): end the reply with the ready item and `/bc-pipeline-to-done`, and do not offer to build it in this session.

## Guard rails
- This is **planning, not building** — do not write implementation code here. Code is the executor's job, one slice at a time. A go-ahead does not change this (step 2).
- The grill and the dependency question (steps 1–2, or the open-questions batch from a settled source) are the human checkpoint; slicing does not wait for approval. Everything after step 2 runs without the user, and the drain runs AFK, so resolve open branches now — a vague issue becomes a parked issue at execution time.
- If the source is an existing GitHub issue, run `/bc-triage` first when it lacks an Agent Brief, has conflicting labels, or may be already implemented / out of scope.
- If planning depends on uncertain state logic, UI direction, or architecture shape, use `/bc-prototype` or `/bc-improve-codebase-architecture` before final PRD/slice publication; capture the verdict in the PRD rather than sending throwaway work to the drain.
- Keep research/evidence distinct from actual PRDs: exploratory notes and reports can feed the PRD (and may be filed in the change folder as evidence), but only the work item's requirements (or `docs/changes/<change-slug>/prd.md` without a table) are the PRD artifact — the parent issue just points at it.

For glossary discovery in legacy projects, follow `bc-domain-modeling`’s legacy glossary rule.
