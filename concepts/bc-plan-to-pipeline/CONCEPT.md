# Concept: bc-plan-to-pipeline

User-invoked planning orchestrator that runs the whole interactive planning front of the loop in one command: `grilling` → `domain-modeling` + `naming-things` (inline) → `prd-drafting` → publish PRD parent issue → `plan-slicing` (agent-finalized, no approval stop) → publish dependency-ordered `ready-for-agent` slice issues. It can be fed by `/triage`, `/prototype`, or `/improve-codebase-architecture` when an issue/backlog/design question needs intake or evidence first. Hands off to `bc-drain-issues` for autonomous execution. The `bc-` prefix is the user's personal namespace.

## Design decisions

- **`Kind:` when it fits (owner decision 2026-11-24).** The item gets a `Kind:` line from the list when one fits (an upstream item's is kept), and its place in `work/order.md` follows `work_index.py --check`: placement by kind, not by skill, below the existing top group so new items cannot flood ahead of the owner's.
- **Exists to remove sequencing burden** (user's request). The planning behaviors once sat behind separate wrappers; the user didn't want to remember the former sequence (`grill-me` → `to-prd` → `to-issues`). This collapses the front into one invocation. The stateful `grill-me` wrapper was removed 2026-09-27; use `grilling` + `domain-modeling` directly for a standalone interview and domain capture.
- **Composes model-invoked disciplines only — option (c) refactor.** Rather than calling single-step user-invoked wrappers (which would break the no-orchestrator-calls-orchestrator boundary), it inlines `grilling`, `domain-modeling`, `naming-things`, `prd-drafting`, and `plan-slicing`. The drafting/slicing disciplines were extracted from their publication orchestrators specifically to make this clean (see those concepts). No behavior is duplicated.
- **Owns publication itself.** The disciplines don't publish; this orchestrator runs the two `gh issue create` steps (parent PRD issue, then slices in dependency order). Keeps publishing in one place for the pipeline run.
- **Publishes a PRD parent issue, but not as drainable work.** Resolved open question from the plan: yes, publish the PRD as a parent issue and reference it as `## Parent` from each slice, for parent/child traceability. The parent is a coordination artifact and is not labeled `ready-for-agent`; only implementation slices enter the drain queue.
- **One human gate, then AFK.** The grill (step 1) is interactive; everything after is autonomous. The slicing quiz was removed 2026-11-24 (owner decision: the owner trusts model slicing, and the stop kept the pipeline from running on its own); a user who asks to review slices first still gets a draft and a wait. The body states this explicitly so unresolved scope is closed before `/bc-drain-issues` runs, where a vague issue becomes a parked issue.
- **Agent Brief quality at publication.** Slice issues now carry an Agent Brief-equivalent contract so `ready-for-agent` means drainable, not merely labeled. Research/evidence artifacts are kept distinct from actual PRDs and drainable slices.
- **Optional upstream evidence, no nested orchestrators.** `triage`, `prototype`, and `improve-codebase-architecture` are user-invoked tools that feed planning. The bc planner can recommend them when needed, but does not call them as nested orchestrators.
- **Recommends the handoff.** Close-out points at `/bc-drain-issues` so planning ends pointing at execution (the loop's two halves).
- **Living specs step (2026-07-12, from OpenSpec).** After the PRD parent is published, resolved requirements are merged into `docs/specs/<area>.md` as normative current truth, tagged `(pending #<parent>)` until the queue drains. Adopted from OpenSpec's archive-merge idea: PRDs/issues go stale by design, so without this nothing durable records *what the system must do* — glossary.md holds vocabulary and ADRs hold decisions, but not requirements. Runs at plan time (not post-drain like OpenSpec's archive) because the human gates are the point of maximum shared understanding and this pipeline hands off to an AFK executor; the pending tag makes plan/implementation drift detectable. Placed after parent publication so the tag can carry a real `#NN`.
- **Per-change folder (2026-07-12, from OpenSpec).** `docs/changes/<change-slug>/` is the single physical home for a change's planning artifacts: `prd.md` (canonical PRD), `tasks.md` (dependency-ordered slice manifest with real issue `#NN`s), plus filed pre-planning evidence (prototype verdicts, architecture-review excerpts, which previously died as temp files). The GitHub queue **stays** — `bc-drain-issues`, triage, and multi-machine claim semantics depend on it — but state is never duplicated: the parent issue body is a summary + pointer (not a PRD copy), slice issues keep full Agent Briefs (AFK workers need self-contained contracts), and `tasks.md` is a map, not a status board (completion state lives only in the tracker). Adapted from OpenSpec's per-change artifact folder; their folder-as-queue model was rejected because this loop's executor drains GitHub issues.

- **Visible-layout projects: the plan is a work item (2026-11-12).** The body resolves glossary, decisions, work-planned, ideas, research and requirements in the project's "Where things go" table (`.bc-agent/AGENTS.md`). With a table, planning produces a work item in work-planned instead of `docs/changes/<slug>/`: a small plan (one slice; since 2026-11-22 regardless of tracker) is `NNN-slug.md` from `.bc-agent/templates/work-item.md` with a `## Requirements` section; a large plan is a folder `NNN-slug/` with two files, `plan.md` (the template; `Issue:` holds the parent, `## Steps` are the slices in dependency order with their issue numbers) and `requirements.md` (the PRD). Rejected alternatives: a separate `slices.md` or one file per slice, which would duplicate the step list and drift; `prd.md` as the name, rejected because the layout reserves "PRD" for the product-level spec (`docs/PRD.md`) and calls a feature's version its requirements. Living specs are merged into the requirements role only when the project has a product-level spec. Items are numbered only from the main checkout; in a worktree the pipeline stops after step 2 (capture), adds an ideas line, and resumes from step 3 in the main checkout, since steps 3–8 write into the item. In a hybrid project the body points to `domain-modeling`'s shared-glossary rule rather than restating it (W3 review, 2026-11-12). Without a table the previous paths stay: the `planning-workflow.md` vault mapping when present, otherwise `docs/changes/<slug>/` (`prd.md`, `tasks.md`), `docs/specs/`, `docs/adr/` and `glossary.md`. Provenance: decisions 5, 6, 10–15, 20 and 25 in [the bc-init-agent visible-layout plan](../../docs/plans/implemented/bc-init-agent-visible-layout.md).

- **Renamed from `bc-plan-to-issues`; two modes and a Source line (2026-11-22, owner decision).** The skill now works in any project and files work into the project's work pipeline (a work item), an issue tracker, or both, so "issues" no longer named what it produces. The old name stays as a deploy alias (`DEPLOY_ALIASES` in `scripts/deploy-local-skills.py`) so existing muscle memory keeps working. **No-tracker mode**: when the project has no tracker or the user asks for work items only, every issue step is skipped and the plan is filed as a work item only (large: folder with requirements + `plan.md` whose `## Steps` are the slices with blocked-by and user stories; small, exactly one slice in every mode: one file). **Settled-source mode**: an already-settled design (an architecture review the owner picked candidates from, an approved spec, a finished grilling) is not re-grilled; only the questions it leaves open are asked, in one batch. The mode is decided at the start from the project and stated with its evidence: a tracker is used only when the project already plans in it (`ready-for-agent` issues or `Issue:` lines) or the user plainly asks; a GitHub remote alone, or "file issues if that's how it works", does not count (pressure runs filed issues on both before this was spelled out). (The slicing quiz was a mandatory gate in every mode until 2026-11-24.) The requirements document is named by the project's own term. A filed work item carries `Source: <name>` naming what produced the plan (the upstream skill, or this skill for a raw idea); `bc-init-agent`'s work-item template gained the optional line in the same change.
- **Plan every planned item; `Planned:` marker (2026-11-24, owner decision).** Items filed by other skills or by hand used to start without requirements or slices. Now (a) producers that file planned items run this skill from a settled source on each one after their filing is committed; (b) the project's pickup rule (generated by `bc-init-agent`) runs it on any planned item without a `Planned:` line before the item moves to active. To serve both, an **existing work item** is a settled source planned in place: same number, name, `Source:` and `Kind:`, no second item. Once `## Steps` are written the skill adds `Planned: bc-plan-to-pipeline <YYYY-MM-DD>` under `Source:`; `Source:` still names the producer, so the two lines answer different questions (who filed it, whether it was planned). In an unattended run with an open question the skill files the questions where the owner sees questions, leaves the item unmarked in planned and stops, rather than guessing or waiting. **Orchestrator boundary:** the rule "no orchestrator calls an orchestrator" is kept. A producer's run of this skill comes after the producer's own work is finished and committed, so it is a sequential handoff, not a nested call: neither skill's gates run inside the other's, and the owner's settled answers are passed along instead of re-asked. `bc-drain-issues`, which is AFK, does not run this skill at all; it skips unmarked items as "needs planning".

## Invocation policy change (2026-07-03)

Removed `disable-model-invocation: true`. It forced the user to retype the command even after explicitly asking the agent to route work into the loop (observed in an project B architecture-review session). The interactivity that matters — the grill (and, until 2026-11-24, the slicing quiz) — is preserved by the skill body's human gates, not by who launches the pipeline. The description now scopes model invocation to cases where the user asks for the bc loop, so agents don't self-select it for ordinary implementation requests.
