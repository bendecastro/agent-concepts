# Research: Delivering an interlocking Agent Skills collection

## Summary

As of 2026-11-25, Vercel’s `npx skills add` is the best-evidenced **cross-agent default for standalone skills**. For a suite whose skills call each other, need helper scripts, or launch subagents, offer a **versioned full pack with native adapters**. Keep `npx skills` as an explicitly tested entry point for independent skills or dependency-complete presets. No comparable ecosystem-wide install data establishes a single winner across all channels.

## Findings

1. **Vercel: discovery plus installation, not a universal pack runtime.** **Direct, high.** The [Vercel CLI repo](https://github.com/vercel-labs/skills) and [npm record](https://registry.npmjs.org/skills/latest) identify the tool (`skills@1.9.0` was latest when fetched); [skills.sh](https://skills.sh/) is its directory/leaderboard, and its [API](https://www.skills.sh/docs/api) calls the counts “Total deduplicated install count,” not unique people or cross-channel market share. The [telemetry implementation](https://github.com/vercel-labs/skills/blob/main/src/telemetry.ts) exposes `DISABLE_TELEMETRY` and `DO_NOT_TRACK`. **Inference, medium:** tools with more visible installs here are not necessarily more popular than native plugins; the case for default is reach and adoption in authors’ instructions, not a measured market share.
   - [CLI reference](https://github.com/vercel-labs/skills/blob/main/docs/commands.md): symlink mode “Creates symlinks from each agent to a canonical copy”; `--copy` makes independent copies. The canonical copy is managed by the installer, not a live link to the GitHub checkout. [Installer](https://github.com/vercel-labs/skills/blob/main/src/installer.ts): “Symlink failed, fall back to copy”; it skips links “whose real target escapes the skill root.” [Agent matrix](https://github.com/vercel-labs/skills/blob/main/docs/agents.md): “automatically detects which coding agents you have installed”; all six named agents are listed (`claude-code`, `codex`, `pi`, `opencode`, `cursor`, `gemini-cli`). Targets that share `.agents/skills` are not isolation boundaries; a compatible client can discover those files even if not individually selected. Agent-specific paths still matter, especially Claude Code.
   - [CLI reference](https://github.com/vercel-labs/skills/blob/main/docs/commands.md): project is “(default)”; `-g` is user scope, `-a` targets agent(s), `--list` previews choices, `--skill` selects by name. `list`/`check` can report `modified`/“has local changes” in project scope; `update` accepts selected names and scopes; `remove` accepts names, source or agents. Bulk `--all` “only removes skills recorded in the lock file”; explicit removal by name is different. `install` with no source restores the project lock, and CI mode validates recorded hashes. A lock is not an immutable archive; pin source refs when you need reproducible fetches. Re-run `add` to discover newly added skills, as [Matt Pocock’s instructions](https://github.com/mattpocock/skills#installation-30-second-setup) note (“re-run `add` to pick up new skills”).
   - Collision vs update: same destination is dangerous before an agent ever sees it. The [CLI reference](https://github.com/vercel-labs/skills/blob/main/docs/commands.md#renaming-a-skill) says “installing the second one overwrites the first”; `--rename` rewrites the folder / `name` / lock key for one skill, not the prose in dependent skills. Restore takes files that differ and restores them from source unless protected by a failing frozen check. Installer source says “clean and create” by removing the destination, and [update source](https://github.com/vercel-labs/skills/blob/main/src/update.ts) installs the replacement via `installToTargets`; **inference:** don’t promise merges or preservation of edits, even in copy mode. Back up/commit edits and fork or separate overrides.

2. **Native routes and composition differ by runtime.** **Direct, high** for the documented capabilities; target surface/version caveats below.

   | Host | User delivery and interaction with local skills |
   |---|---|
   | Claude Code | [Install docs](https://code.claude.com/docs/en/discover-plugins): `/plugin marketplace add owner/repo` registers a catalog, then `/plugin install plugin@marketplace`; user/project/local scopes, and “Committing that entry … doesn't download it to their machines.” [Skill docs](https://code.claude.com/docs/en/skills): filesystem names resolve “Enterprise over personal, and personal over project”; `/plugin-name:skill-name` coexists with a local same-name skill; folder symlinks resolve to their target and are deduplicated. [Marketplace hosting](https://code.claude.com/docs/en/plugins/host-marketplace): custom-marketplace auto-update is “off … by default”; new plugin version is required for a new cache copy. It supports plugin dependency version ranges and cross-marketplace allowlists, not a cross-agent skill dependency declaration. Symlinks outside the marketplace are skipped; targets elsewhere in the same marketplace can be copied into the cached plugin. |
   | Codex | [OpenAI skill docs](https://developers.openai.com/codex/skills): reads repo ancestor and user `.agents/skills` plus admin/system roots; “supports symlinked skill folders”; same `name` means “both can appear in skill selectors.” Disable by absolute path or name in `[[skills.config]]`; `agents/openai.yaml` can declare **tool** dependencies and invocation policy. [openai/skills](https://github.com/openai/skills) ships system skills and documents `$skill-installer` for curated, experimental or direct GitHub paths. [OpenAI plugin packaging](https://developers.openai.com/plugins/build/plugins) gives `codex plugin marketplace add owner/repo`, personal/repo catalogs, and a cache path; recommends root `plugin.json` compatible with Agent Plugins, with `.codex-plugin/plugin.json` as fallback. Public-directory lifecycle-hook eligibility and manual desktop trust differ; do not promise identical behavior across CLI, desktop and cloud. |
   | Gemini CLI | [Skill management](https://geminicli.com/docs/cli/using-agent-skills/) documents `gemini skills install` (Git or local `.skill`, default user, `--scope workspace`), `link`, `uninstall`, `/skills reload`, enable/disable; “the version from the higher-precedence location is used”: workspace > user > extension > built-in. `.agents/skills` aliases are supported. [Extensions](https://geminicli.com/docs/extensions/) and [extension authoring](https://geminicli.com/docs/extensions/writing-extensions/) document native bundles with `gemini-extension.json`, and Superpowers documents `gemini extensions install` / `update`. **Market caveat:** Google’s [transition notice](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/) says individual/free/Pro/Ultra requests stop on June 18, 2026, but “will remain accessible via paid Gemini and Gemini Enterprise Agent Platform API keys”; qualifying enterprise access also continued at the announcement. For new individual users, test Antigravity separately; do not count Gemini CLI and Antigravity as interchangeable. |
   | Cursor | [Cursor Skills](https://cursor.com/docs/context/skills): discovers `.agents/skills`, `.cursor/skills`, their user counterparts, plus Claude/Codex compatibility paths; “Skills aren't imported on their own” for the GitHub import flow, which uses `.cursor-plugin/marketplace.json` and plugin install. Local `~/.agents/skills` is not copied to Cloud Agents/remote SSH; sync applies to `~/.cursor/skills`, and automation needs repo-scoped skills. General duplicate-name winner **unverified**; test it, don’t infer from search order. |
   | OpenCode | [V2 skill docs](https://opencode.ai/docs/skills/): project/global `.opencode`, `.agents`, `.claude` roots and explicit config/HTTP catalogs; “the source registered later supplies the skill,” and the ID is path-derived. Explicit config > native project > native global > `.agents` > `.claude` > built-ins. `skill` permissions can hide/deny it. [Plugins](https://opencode.ai/docs/plugins/) and [Superpowers OpenCode install](https://github.com/obra/superpowers/blob/main/.opencode/INSTALL.md) show Git/npm plugin infrastructure and distinguish V1 `plugin` vs V2 `plugins`; V2 integration requires the documented minimum. Do not project the V2 precedence rule onto V1 without testing. |
   | Pi | [Skills docs](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/skills.md): `.agents/skills` plus Pi locations, “Name collisions keep the first discovered skill and produce a warning”; check startup diagnostics and `/skill:name`, `/reload` after edits. [Pi packages](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/packages.md) load “npm, git, or a local path,” optionally include extensions/runtime dependencies, support `--local` trusted project scope, `pi list`, `pi remove`, `pi update --extensions`, pinned versions/refs, and resource include/exclude filters. “A project entry normally replaces the personal entry” **for the same package**, distinct from same-name skills from unrelated packages. Local-path packages run “without copying.” |

3. **What authors actually ship.** **Direct, high.** [Superpowers](https://github.com/obra/superpowers#installation): “Installation differs by harness”; leads with official/custom Claude marketplaces, official Codex plugin, Cursor marketplace, Gemini extension, `pi install git:github.com/obra/superpowers`, and a native OpenCode adapter; Pi subagent/task tools are “optional Pi companion packages,” so skill files alone aren’t the full integration. [Anthropic’s collection](https://github.com/anthropics/skills): `/plugin marketplace add anthropics/skills` then `document-skills` or `example-skills`; includes a skills.sh badge, and documents Claude.ai and API delivery separately (“upload custom skills”). [Matt Pocock](https://github.com/mattpocock/skills#installation-30-second-setup): Claude/Codex/Copilot plugins, `gemini skills install … --path skills/engineering` and productivity, and `npx skills@latest add … -a <agent>` elsewhere or for editable files. “Pick one per agent, because installing both gives you every skill twice.” [Vercel’s collection](https://github.com/vercel-labs/agent-skills#installation) leads with `npx skills add vercel-labs/agent-skills` and says each change publishes an “immutable GitHub release” for its discovery index.

4. **Other delivery formats are useful, but not equally established.** **Direct, high** for existence; adoption **unverified** beyond the named examples.
   - npm: [Vercel CLI docs](https://github.com/vercel-labs/skills/blob/main/docs/commands.md#skills-sync) document experimental `experimental_sync` that “Sync[s] skills from npm packages and `package.json` declarations” (including a declarative `skills` list with npm/Git sources). It links paths from installed packages, can include/exclude, supports frozen CI, and “a directory or link that sync did not create is never replaced.” This is not ordinary `npm install` alone. Pi has the established native npm path above; OpenAI [packaging docs](https://developers.openai.com/plugins/build/plugins) likewise document an npm-backed plugin source (“The `npm` CLI must be installed”). [Skild](https://skild.sh/) offers `npm i -g skild` with `install`, `update`, `uninstall`, `publish`; no comparative uptake verified. [Homebrew](https://formulae.brew.sh/formula/skills) has `brew install skills` for **the installer**, not a general registry where your SKILL.md is discovered. No widely adopted pipx skill-delivery route verified; Python packaging here is evidenced for the validator, not for agents’ skill discovery.
   - Plain Git checkout + links: a legitimate low-level route; [Superpowers OpenCode docs](https://github.com/obra/superpowers/blob/main/.opencode/INSTALL.md) explicitly call the predecessor “the old symlink-based install” using `git clone`, and Claude/Codex explicitly follow loose-folder links. **Inference:** one pinned checkout can deliberately preserve the repo’s topology and let users audit updates, selectively link entries and unlink on removal. It also makes you responsible for correct real paths, platform link support, rollback, and remote/cloud packaging. Unlike the canonical copy made by `npx`, linking the whole tree does not break sibling paths by copying them away from the original hierarchy; verify each host’s actual loader/path resolution.
   - Emerging shared wrapper: [Agent Plugins 1.0](https://agent-plugins.org/) specifies `plugin.json`, `skills/`, `mcp.json` and client extensions; its own wording leaves “distribution, installation, permissions, user experience, and client-specific capabilities … under each client’s control.” OpenAI documents it; Cursor is represented on the spec’s steering committee. **Inference:** design a reusable packaging core, but do not infer equivalent runtime support or replacement of existing manifests on all targets.

5. **Composition strategy: dependencies and customization without collisions.** **Direct, high** on format; recommendations are **inference**. The [spec](https://agentskills.io/specification) defines a skill as a directory, recommends “relative paths from the skill root,” and says scripts should be “self-contained or clearly document dependencies”; it has no portable cross-skill dependency resolver, override/merge layer, or subagent invocation contract. Keep references/scripts inside each standalone skill payload, or keep the entire relevant graph in one native artifact. Direct-path references to siblings can work on a preserved tree, but not after a subset install, rename, filename flattening, or cache rearrangement. The [open Vercel grouping request](https://github.com/vercel-labs/skills/issues/992) from a maintainer with “39 skills organized into 6 tracks” is evidence of real onboarding friction, not proof of a portable `--group` feature. Compute closure from your graph; publish a few curated presets; missing hard dependencies should fail with a setup hint, optional ones should degrade. [Matt Pocock’s setup ADR](https://github.com/mattpocock/skills/blob/main/.agents/adr/0001-explicit-setup-pointer-only-for-hard-dependencies.md) explicitly splits “hard-dependency” and “soft-dependency” skills and stores issue tracker/labels/docs configuration per repo. Use a publisher-prefix for loose public IDs and qualified calls where native; never use same-name shadowing as your cross-agent customization contract. Keep choices in project configuration or separate user-owned overlays, and structural edits in a fork or deliberately unmanaged copy. Native plugin caches are upstream-owned; update the artifact, not users’ overlays (Claude exposes `${CLAUDE_PLUGIN_DATA}` that “survives plugin updates” per [skill docs](https://code.claude.com/docs/en/skills)). If exact source matters, record which skill/version the parent and child loaded. Inspect third-party code before installing a bundle: [Pi packaging docs](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/packages.md) explicitly say “Packages can execute extension code” and skills can instruct the model to run programs.

6. **Verification needs three levels.** **Direct, high** for examples; proposed matrix **inference**.
   - **Format and graph:** [Agent Skills spec](https://agentskills.io/specification#validation) gives `skills-ref validate ./my-skill`: “checks that your `SKILL.md` frontmatter is valid and follows all naming conventions.” That is not a cross-file or behavior test. [Example CI](https://github.com/marcfargas/skills/blob/main/.github/workflows/validate.yml) installs Python `skills-ref` but invokes `agentskills validate`, so pin the validator build and verify its binary spelling; do not assume every release has both aliases. Add your own checks for links, graph closure, canon/pack content equality, manifests, helper executable bits/runtime prerequisites and unexpected omissions.
   - **Install and runtime smoke:** the [same workflow](https://github.com/marcfargas/skills/blob/main/.github/workflows/validate.yml) checks `pi list`, uses `export HOME=$(mktemp -d)`, and exercises `skills add --list`, all skills and individual installs. Some of its checks grep installer text, not loaded contents. [Superpowers testing](https://github.com/obra/superpowers/blob/main/docs/testing.md) separately tests “OpenCode plugin loading, bootstrap caching, and tool registration” and Codex packaging sync. Use isolated HOME *and* clean worktree/config, install from the actual tagged/released package, assert concrete files and resolved versions in the runtime, explicitly invoke one skill, traverse a dependency, run a harmless helper, and test one child launch on supported hosts. Include update/remove, a same-name user skill, an existing symlinked config root, scope boundaries and Windows if claimed. Record harness/version, OS, channel and supported surfaces; split “discovery,” “invocation,” “scripts,” “child/hook,” and “behavior,” not one giant check mark. Vercel’s [supported agents table](https://github.com/vercel-labs/skills/blob/main/docs/agents.md) is a feature/discovery starting point (“some features may be agent-specific”), not behavioral certification.
   - **Behavior:** [Agent Skills evaluation guide](https://agentskills.io/skill-creation/evaluating-skills) says test “once with the skill and once without it (or with a previous version)” and measure variance only with repeats. [Superpowers methodology](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md) describes “pressure scenarios with subagents” with an observed fail/pass cycle; its [test docs](https://github.com/obra/superpowers/blob/main/docs/testing.md) say Quorum “drives real coding-agent CLIs” and grades with “deterministic post-checks” plus LLM assessment, separating static public CI from live evals. Isolate no-skill baselines so they cannot discover the skill through aliases, plugins, or disk; test both automatic selection and explicit invocation, grade artifacts/tool traces as well as responses, and report harness/model/ref plus scenario and pass counts. Run trusted live evals separately from untrusted PRs.

## Reported failures

These are direct evidence of **reports**, not incidence estimates or independent reproductions.

- [Vercel #456](https://github.com/vercel-labs/skills/issues/456): when the skills directory “is itself a symlink,” relative links resolved at the wrong physical location (dotfiles/profile setups). Closed by [#2283](https://github.com/vercel-labs/skills/pull/2283); current installer source calculates from real directory. Regression-test this, don’t present it as an unfixed current bug.
- [Vercel #1199](https://github.com/vercel-labs/skills/issues/1199): update “replaces those copied files with symlinks,” causing portability issues; closed by [#2607](https://github.com/vercel-labs/skills/pull/2607), and current source carries `installMode`. [Vercel #1718](https://github.com/vercel-labs/skills/issues/1718) remains open: reports `remove -a <subset>` dropping the lock entry and `update` re-linking to “all installed agents.” Current update source still describes target resolution as “what `add -y` would pick”; exact behavior on all 1.9.0 paths untested.
- [Vercel #1603](https://github.com/vercel-labs/skills/issues/1603): root skill install reportedly lost companion `scripts/` / `references/`; closed by [#1609](https://github.com/vercel-labs/skills/pull/1609). Distinguish this packaging bug from intentional exclusion of out-of-root file links.
- [Superpowers #1082](https://github.com/obra/superpowers/issues/1082): one Windows Claude update left “only metadata directories,” despite installed/enabled UI. Maintainer says “Please file upstream”; closing this report does not prove a Claude installer fix. Always smoke-test the updated artifact, not just the enabled flag.
- [Codex #30993](https://github.com/openai/codex/issues/30993): open report that explicit `$superpowers` “resolved to the stale cached openai-curated copy,” despite another plugin being enabled. Comments report stale staging copies selected by a child and a remote cache variant for which the original disable workaround did not suffice. One install channel per agent and resolved-version checks are more defensible than assuming a universal precedence rule.

## Contradictions and missing evidence

- Superpowers [release history](https://github.com/obra/superpowers/releases) first said “Gemini CLI support removed,” then “Gemini CLI support is restored”; current README includes it. Google’s primary announcement distinguishes consumer from paid API/enterprise access. Do not use the earlier release note as evidence Gemini CLI is universally gone. Later [Google Cloud FAQs](https://docs.cloud.google.com/gemini/docs/codeassist/sunset) also detail Code Assist subscription sunset; late-November install/auth on the remaining routes was not run here.
- Describing skills.sh as “copies editable files” ([Matt Pocock README](https://github.com/mattpocock/skills)) is compatible with copying into a canonical store plus linking targets; it does not mean the CLI always uses `--copy`. Claimed update automation is channel-specific, particularly Claude custom marketplace opt-in.
- No apples-to-apples install totals for native marketplaces, Vercel, npm, Homebrew or plain Git; no evidence of a mainstream pipx delivery path; no unambiguous Cursor duplicate-name rule verified; no native installation, upgrade or behavioral eval rerun for this research. `source_check` retrieved provider summaries but did not assess semantic support; decision-critical claims above were checked manually in the original docs/source instead. Deprioritized generic tutorials and forked Superpowers install docs in favor of vendor docs, upstream README/release history, source and actual issue threads.

## Ranked recommendation

1. **Full pack: versioned Git release plus native packaging where it earns its keep.** Keep one canonical source and generate/test manifests/artifacts; lead with a Claude marketplace plugin and Pi Git package for the most integrated behavior, then add Codex/Cursor native packages where their capability matrix justifies it. Treat OpenCode version adapters and Gemini CLI/Antigravity as distinct targets. Preserves layout, allows bootstrap/agent wiring where supported, and gives versioned updates; costs per-harness maintenance, and plugin approval/scope/cache behavior varies. Use separate read-only package content and writable user/project settings.
2. **Discovery/front door: `npx skills add` for self-contained entries and tested dependency-complete presets.** Lowest-friction cross-agent reach and subset install; not the sole installer for the orchestration pack. Prefix exported names, document explicit `-a` and project/global choice, and warn not to install both routes into identical discovery surfaces. Avoid relying on experimental npm sync until you have an actual npm-consumer need and CI coverage.
3. **Auditable fallback: pinned `git clone` plus non-clobbering links.** Best escape hatch and local author path when full topology matters and no native wrapper is ready. More user effort and OS/cloud differences; provide deterministic install/check/uninstall instructions, skip existing skills by default, and show what will change on update.

**Next step:** package and smoke-test two representative slices before adding manifests everywhere: a truly standalone skill with a helper, and one parent/child workflow with real sibling dependencies. Exercise both next to a user skill and preserve the exact installed file/version evidence.
