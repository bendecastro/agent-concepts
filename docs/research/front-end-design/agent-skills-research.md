# Research: coding-agent UI design skills and evidence

Scope: primary sources on frontend skills, visual-review workflows, and applicability beyond websites. Findings and limitations recorded incrementally.

## Primary skill guidance

1. **Anthropic frontend-design** ([skill](https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md)): frontmatter trigger: “Guidance for distinctive, intentional visual design when building new UI or reshaping an existing one.” Also names aesthetic direction and typography. Direct evidence: establish product, audience and job; confirm missing subject; build compact color/type/layout tokens and ASCII wireframes, critique plan against brief before coding; deliberate typography, restrained motion and functional copy; respect existing brief; screenshots if supported, mobile, focus and reduced motion. This is author guidance, not controlled evidence tokens or screenshots cause improvements. Confidence high.
2. **OpenAI frontend-skill** ([GPT-5.4 guide, including full skill](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4)): frontmatter: “Use when the task asks for a visually strong landing page, website, app, prototype, demo, or game UI.” Proposes visual/content/interaction theses, composition before components, brand, narrative, restrained cards and app-specific workspaces; existing systems take precedence. Guidance recommends references, tokens, real content and Playwright visual/behavioral checks. Claimed Playwright improvement is vendor assertion, no quantitative comparison supplied in article. Confidence high for wording, low for effectiveness. The linked original GitHub path returned 404; the skill quoted here is the first-party article's embedded version.
3. **OpenAI current GPT-5.5 prompt** ([guide](https://developers.openai.com/api/docs/guides/frontend-prompt)): applies when building frontend experiences; respects existing design and task domain; explicitly distinguishes utilitarian operational apps from expressive games, asks for fit, stable layout, usable controls and screenshots/pixel checks for 3D. Its hard-coded typography, card, icon, palette and hero rules are model-specific defaults, not universal design laws. Confidence high.
4. **Vercel web-design-guidelines** ([skill](https://raw.githubusercontent.com/vercel-labs/agent-skills/main/skills/web-design-guidelines/SKILL.md), [rules](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)): frontmatter: “Review UI code for Web Interface Guidelines compliance”; triggers on review UI, accessibility, design/UX audit and best practices. Fetches latest rule text, reads requested files, returns `file:line` findings; asks for file pattern if missing. This is code review rather than a complete visual design process. Confidence high.

## Concrete iterative council case

5. **T3 Code #24776** ([PR](https://github.com/pingdotgg/t3code/pull/24776)): after human designer criticized font, radius, icons, hierarchy, authors changed shared tokens/primitives, compared Linux light/dark screenshots and report three reviewer rounds. Their scores 6–6.5 initially and 9 at final are self-reported, unblinded observations—not independent evidence of human preference or causality. One judge mistook downscaled screenshot text for clipping; 1:1 crops led to rescoring without a code change. Code review also flagged global icon stroke and disabled state issues; resolution unknown. The PR was superseded by #24865. Confidence high for report; no causal conclusion.
6. **T3 Code #24837** ([PR](https://github.com/pingdotgg/t3code/pull/24837)): five rounds from fresh screenshots with seeded data, 1280×832 macOS and reference applications. Opus and Sol scored T3 above both references; Muse scored 7.9 versus Claude Code 8.1, and had not rescored final partial changes. Same council judged repeated rounds, making score optimization/judge overfitting a plausible **researcher inference**, not a demonstrated event. Independent automated review raised lost Git actions, completion feedback and touch-discoverability risks; resolution unknown. The PR was superseded by #24865. Confidence high for reported facts.

## Further sources and evidence

7. **Anthropic aesthetics article** ([article](https://claude.com/blog/improving-frontend-design-through-skills)) attributes generic output to distributional convergence, illustrates same-prompt before/after skill examples, and prescribes actionable type, theme, motion, backgrounds and avoiding substitution of one cliché with another. It is a qualitative vendor demonstration, not blinded evaluation or proof of its proposed causal mechanism. Its older suggestion to avoid Inter categorically is context-sensitive: T3 #24776 deliberately adopts Inter on Windows/Linux to fix weight availability ([PR](https://github.com/pingdotgg/t3code/pull/24776)). Support: direct; confidence high on reported guidance.
8. **Impeccable** ([skill](https://raw.githubusercontent.com/pbakaus/impeccable/main/.agents/skills/impeccable/SKILL.md), [repository](https://github.com/pbakaus/impeccable)): description starts “Use when the user wants to design, redesign, shape, critique, audit, polish, simplify, harden, animate, or otherwise improve a frontend interface” and includes native iOS/Android; excludes backend-only. Distinguishes Persuade, Operate, Read and Experience; detects existing visual truth, preserves it for refinement, scales visual ambition to surface, verifies rendered results and batches corrections. Separates critique, technical audit, adapt and polish; reports native references but HTML/CSS detector and live browser remain web-only. Repo claims 62 deterministic checks, not their accuracy or UX outcome; treat as product claim. Confidence high for documented design.
9. **Community design-review** ([skill](https://raw.githubusercontent.com/julianoczkowski/designer-skills/main/design-review/SKILL.md)): frontmatter: “Run a structured design critique against the brief and codebase.” Trigger includes review, QA or polish after building. Takes brief and changed components, requires desktop/tablet/mobile screenshots plus relevant states and dark theme, returns screenshot-linked, file/line-specific must/should/could findings, preserves positives, and writes a review document. It is a skill, not proven to enforce read-only review: it writes its report and screenshots. Fixed breakpoints are examples, not substitutes for target devices. Confidence high.
10. **A concrete independent visual reviewer** ([Impeccable finish reviewer](https://raw.githubusercontent.com/pbakaus/impeccable/main/.claude/agents/impeccable-finish-reviewer.md)): frontmatter describes finished-build review and ordered fixes; disallows Write/Edit/NotebookEdit and parent applies fixes. Inputs include original brief, user answers, screenshots, direction contract, product context, existing detector findings and, when applicable, approved comp and region comparisons. It cannot browse or capture; validates screenshot evidence first and demands recapture if absent/malformed. Returns disposition plus fidelity matrix, ordered material fixes and what to keep; after fixes requires fresh captures rather than trusting parent narration. Its many opinionated comp-specific mandates and tool permissions are implementation choices, not proven universal. Confidence high.
11. **Visual feedback ablation** ([WebGen-Agent paper](https://arxiv.org/html/2509.22644)): authors report screenshot feedback increased measured appearance score from 3.0 to 3.6 in one workflow ablation, while adding GUI-agent tests slightly decreased appearance; backtracking/select-best mitigated that loss. This is experimental support within this benchmark and setup, not proof that every screenshot loop or separate reviewer improves human-rated design; judge and system choices limit generalization. Confidence medium. Automated `source_check` semantic verdict was unavailable; original paper inspected directly.
12. **Judge reliability** ([MLLM as UI Judge](https://arxiv.org/html/2510.08783)): 30 static interfaces assessed against crowdsourced humans; tested older models show some correlation on aesthetics and near-chance pairwise performance around 50% for ease of use. Stronger preference gaps were easier; screenshots alone miss interactive usability. This does not measure newer model accuracy. ([ArtifactsBench](https://arxiv.org/html/2507.04952)) reports up to 90.95% pairwise agreement with experts for checklist-guided code plus screenshot evaluation, a different setup; authors acknowledge fixed-interval captures limit interaction coverage. Neither result validates an arbitrary 9/10 as objective quality. Automated `source_check` semantic verdict was unavailable; paper inspected directly. Confidence high for reported findings, medium for generalization.

## Non-web guidance

13. **Platform-specific constraints:** Impeccable explicitly routes iOS/Android to platform guidance and has native audit/adapt ([repository](https://github.com/pbakaus/impeccable)); [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/) and [Android accessibility](https://developer.android.com/guide/topics/ui/accessibility/apps) provide native authorities. Chrome extension UI is HTML in a popup, but its constrained, transient surface should not inherit marketing-page hero assumptions; popup API and basic structure are documented by [Chrome](https://developer.chrome.com/docs/extensions/develop/ui/add-popup), and [Chrome accessibility](https://developer.chrome.com/docs/extensions/how-to/ui/a11y) covers readable/scalable UI. The popup adaptation is researcher inference. TUI-specific agent design skill and empirical tests were not verified; use [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/) as cross-platform accessibility guidance, not proof of TUI-specific agent effectiveness. Confidence medium.

## Contradictions and weaknesses

- Anthropic's current skill prefers one orchestrated motion and sparing automatic animation ([skill](https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md)), while OpenAI's embedded GPT-5.4 skill prescribes 2–3 motions for visually led work ([article](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4)). Treat as context-dependent, not a universal quota.
- Marketing-specific full-bleed heroes and aesthetic font bans can degrade dense tools, native screens or established systems; GPT-5.5 itself distinguishes operational products ([guide](https://developers.openai.com/api/docs/guides/frontend-prompt)). This is researcher interpretation.
- Code-only audits miss rendered behavior, but screenshot-only review misses semantics and state changes; PR #24837's reported Git/touch findings illustrate the latter ([PR](https://github.com/pingdotgg/t3code/pull/24837)).
- Scores can drift as context, presentation and judges vary: the downscaled crop correction is directly observed in #24776; repeated-judge overfitting is an unverified risk, not established in these PRs ([PR](https://github.com/pingdotgg/t3code/pull/24776)).

## Missing evidence and next steps

- No controlled source found establishing tokens-first or reference screenshots alone improve real-world user outcomes across UI types. Separate reviewer vs self-critique, score drift and judge overfitting were not isolated by a controlled UI experiment here.
- Original OpenAI skill repository path returned 404; the first-party guide reproduces a version but current repository canonical path remains unverified.
- Native desktop, TUI and extension-popup agent skill examples remain unverified. Useful follow-up: run blind, human-rated comparisons and task tests with/without image critique and independent reviewer, across a real app, native UI and TUI; hold captures, fixtures, prompts and evaluation criteria fixed.
- Sources kept are linked inline; secondary SEO skill listings were deprioritized in favor of repository files, official platform guidance and papers.

## What this means for the skill

**Researcher recommendations:** trigger broadly for any user-facing surface but classify operating context before applying patterns; preserve existing systems and user references. Specify design intent and a minimal semantic token plan proportional to scope, not an automatic redesign. Render and inspect realistic state/viewport captures when possible, use 1:1 crops to verify small defects, and pair visual critique with interaction/accessibility checks. A separate read-only reviewer can receive the brief, constraints, references and valid fresh captures, return evidence-linked prioritized fixes, and demand recapture when evidence is missing; report uncertainty and avoid treating model scores as a ship gate or a replacement for users.
